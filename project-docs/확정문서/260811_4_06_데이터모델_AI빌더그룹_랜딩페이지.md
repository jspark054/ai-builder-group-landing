## 1. 개요

### 1.1 목적

『기능 명세』(ABG-FN-003) §5 관리 화면의 입력 항목과 『정책 정의』(ABG-POL-004)를
**데이터베이스 스키마로 확정한다.**

### 1.2 기술 전제

| 항목 | 결정 | 근거 |
|---|---|---|
| DB | **PostgreSQL** (Supabase) | `REQ-C-001` orca-ai-company 기반 |
| 인증 | **Supabase Auth** | G-4 확정 |
| 권한 | **RLS (Row Level Security)** | `REQ-N-011` 서버 강제 |

**RLS를 쓰는 이유가 요구사항에 있다.** `REQ-N-011`은 *"권한 경계를 서버에서 강제한다.
프론트엔드 은닉으로 대체하지 않는다"*를 P0로 규정한다. **DB가 직접 막는 구조가 이를 만족한다.**

### 1.3 명명 규칙

| 대상 | 규칙 |
|---|---|
| 테이블 · 컬럼 | `snake_case`, 단수형 (`builder`, `project`) |
| 기본키 | `id` — `uuid`, `gen_random_uuid()` |
| 외래키 | `<대상>_id` |
| 시각 | `timestamptz`, `created_at` · `updated_at` |
| 불리언 | `is_` 접두 |

### 1.4 공통 컬럼

**모든 테이블에 아래를 둔다.** 표에서는 생략한다.

| 컬럼 | 타입 | 기본값 |
|---|---|---|
| `id` | `uuid` | `gen_random_uuid()` |
| `created_at` | `timestamptz` | `now()` |
| `updated_at` | `timestamptz` | `now()` — 트리거로 갱신 |

`updated_at`은 `FN-A06`의 *"최종 수정 일시 표시"*에 쓴다.

## 2. 엔티티 관계

```
auth.users ──1:1── builder ──┬──N:M── project ──N:M── category
                              │      (project_builder)  (project_category)
                              │
                              ├──N:1── course
                              │
                              └──1:N── insight                  (v3.1)

admin_user ──1:1── auth.users        운영팀 계정 (복수)
```

| 관계 | 카디널리티 | 결정 근거 |
|---|---|---|
| `builder` ↔ `project` | **N:M** | G-3 확정 |
| `project` ↔ `category` | **N:M** | D-4 회신 + 팀 협의 (단일 목록 + 태그) |
| `builder` → `course` | N:1 | 수료 과정 1개 |
| `auth.users` → `builder` | 1:1 | Supabase Auth 연결 |
| `builder` → `insight` | **1:N** | 글마다 작성 빌더 1명 (`REQ-F-095`). 익명 글을 두지 않으므로 NOT NULL |

## 3. 테이블 정의

### 3.1 `builder` — 빌더

| 컬럼 | 타입 | NULL | 기본값 | 제약 · 근거 |
|---|---|:---:|---|---|
| `auth_user_id` | `uuid` | ○ | | FK → `auth.users(id)`. **UNIQUE.** 계정 미발급 시 NULL |
| `slug` | `text` | ✕ | | **UNIQUE.** URL용. 발행 후 변경 금지 (`REQ-N-013`) |
| `display_name` | `text` | ✕ | | ≤ 40자. 표기명 (`POL-12`) |
| `name_type` | `text` | ✕ | `'nickname'` | `real` / `nickname` (`POL-12`) |
| `image_url` | `text` | ○ | | **NULL 허용** — 미등록 시 폴백 (`POL-02`) |
| `image_alt` | `text` | ○ | | 이미지 등록 시 **필수** (`FN-A02-06`) |
| `cohort` | `int` | ✕ | | **정수.** 표기는 `${cohort}기` — 아래 주의 |
| `bio` | `text` | ○ | | ≤ 200자. 한 줄 소개 |
| `career` | `jsonb` | ✕ | `'[]'` | 이력 배열. **표기 상한 5개** (`POL-05`) |
| `course_id` | `uuid` | ○ | | FK → `course(id)` |
| `is_public` | `boolean` | ✕ | `false` | **admin만 변경** (`FN-A02-08`) |
| `is_pinned` | `boolean` | ✕ | `false` | 상단 고정 (`FN-A02-09` · `REQ-F-020a`) |
| `pin_order` | `int` | ○ | | 고정 시 순서. `is_pinned = true`일 때만 유효 |
| `meta_title` | `text` | ○ | | ≤ 40자 권장. 초과 시 경고(차단 아님) |
| `meta_description` | `text` | ○ | | ≤ 110자 권장 |
| `og_image_url` | `text` | ○ | | 미입력 시 `image_url` 사용 |

> **`cohort`를 `text`가 아니라 `int`로 둔다.** `text`면 `'10기' < '2기'`로 정렬되어
> **10기에서 목록 순서가 깨진다.** 지금 정하면 0원, 나중에 고치면 마이그레이션이다.

**`career` 구조**

```json
[{ "title": "...", "org": "...", "period": "2024-2025" }]
```

**표기 상한 5개는 화면 규칙**이지 저장 제한이 아니다. 초과분은 접어서 보여준다 (`FN-P06-07`).

### 3.2 `project` — 프로젝트

| 컬럼 | 타입 | NULL | 기본값 | 제약 · 근거 |
|---|---|:---:|---|---|
| `slug` | `text` | ✕ | | **UNIQUE.** 발행 후 변경 금지 |
| `title` | `text` | ✕ | | ≤ 60자 |
| `summary` | `text` | ✕ | | ≤ 120자. 카드 1~2줄 (`FN-C01-03`) |
| `body_what` | `text` | ✕ | | **무엇을 만들었나** |
| `body_why` | `text` | ✕ | | **왜 필요했나** |
| `body_how` | `text` | ✕ | | **어떻게 풀었나** |
| `body_result` | `text` | ✕ | | **결과** |
| `thumbnail_url` | `text` | ✕ | | **필수.** 미등록 시 카드 렌더 제외 (`POL-02`) |
| `thumbnail_alt` | `text` | ✕ | | `REQ-F-064` |
| `live_url` | `text` | ○ | | **NULL 허용** |
| `link_grade` | `text` | ✕ | `'none'` | 5개 등급 (`POL-03`) |
| `is_public` | `boolean` | ✕ | `false` | **admin만 변경** (`FN-A03-14`) |
| `sort_order` | `int` | ✕ | `0` | 수동 정렬 (`FN-A03-15` · `REQ-F-063`) |
| `meta_title` · `meta_description` · `og_image_url` | `text` | ○ | | `builder`와 동일 |

#### 본문을 4개 컬럼으로 나누는 이유

**`03 §4.3`이 4문항을 h2로 렌더하도록 규정한다.** 하나의 `body`에 마크다운으로 넣으면
**소제목이 지켜졌는지 검증할 수 없고**, `FN-A03-06`의 500자 미달 경고를 정확히 계산할 수 없다.

| 방식 | 판정 |
|---|---|
| 단일 `body` (마크다운) | 4문항 구조가 **관례**가 된다. 누락을 못 막는다 |
| **4개 컬럼** | 구조가 **스키마로 강제**된다. 각 문항 NOT NULL |

**최소 500자는 네 컬럼의 합계**로 판정한다 (`POL-04`).

#### `link_grade` 값

| 값 | 의미 | 카드 표기 |
|---|---|---|
| `live` | 운영 중 서비스 | 바로가기 |
| `deploy` | 배포된 결과물 | 바로가기 |
| `repo` | 저장소 | 코드 보기 |
| `video` | 동작 영상 | 영상 보기 |
| `none` | 없음 | **버튼 미노출** (`FN-C01-08`) |

> ⚠️ **확인 필요** — `POL-03`이 5개 등급을 정의하나 **각 등급의 카드 문구가 명시돼 있지 않다.**
> 위 문구는 초안이다. 디자인 단계에서 확정한다.

### 3.3 `project_builder` — 담당 관계 (N:M)

| 컬럼 | 타입 | NULL | 기본값 | 제약 |
|---|---|:---:|---|---|
| `project_id` | `uuid` | ✕ | | FK → `project(id)` `ON DELETE CASCADE` |
| `builder_id` | `uuid` | ✕ | | FK → `builder(id)` `ON DELETE RESTRICT` |
| `is_owner` | `boolean` | ✕ | `false` | **대표 여부.** G-3b 확정 |
| `sort_order` | `int` | ✕ | `0` | 표기 순서 |

**제약**

```sql
UNIQUE (project_id, builder_id)
-- 프로젝트당 대표는 정확히 1명
CREATE UNIQUE INDEX ON project_builder (project_id) WHERE is_owner;
```

**`ON DELETE RESTRICT`를 쓰는 이유** — 빌더를 지우면 프로젝트의 담당자가 사라진다.
**빌더 삭제 전에 담당 관계를 먼저 정리하도록 강제한다.**

### 3.4 `category` — 포트폴리오 분류

| 컬럼 | 타입 | NULL | 기본값 | 제약 |
|---|---|:---:|---|---|
| `axis` | `text` | ✕ | | `industry` / `service`. **필터 그룹 구분용** |
| `slug` | `text` | ✕ | | **UNIQUE.** 2차 필터 도입 시 URL로 씀 |
| `name` | `text` | ✕ | | 표시명 |
| `sort_order` | `int` | ✕ | `0` | 카드 표기 우선순위에도 쓴다 |
| `is_public` | `boolean` | ✕ | `false` | |

**초기 데이터 9건** — 팀 협의로 확정. 임의 지정이며 운영 중 조정한다.

| `axis` | `name` |
|---|---|
| `industry` | 교육 · 커머스 · 의료 · 금융 · 공공 |
| `service` | 랜딩 · 예약 · 대시보드 · 커뮤니티 |

```sql
check (axis in ('industry', 'service'))
```

**계층을 만들지 않는다.** 두 축의 값을 **하나의 목록**으로 관리하고
`axis`는 **필터를 묶는 용도**로만 쓴다. 관리 화면이 하나로 끝나고,
값을 다른 축으로 옮겨도 `axis` 하나만 바꾸면 된다.

### 3.5 `project_category` — 분류 연결 (N:M)

| 컬럼 | 타입 | NULL | 제약 |
|---|---|:---:|---|
| `project_id` | `uuid` | ✕ | FK → `project(id)` `ON DELETE CASCADE` |
| `category_id` | `uuid` | ✕ | FK → `category(id)` `ON DELETE RESTRICT` |

```sql
UNIQUE (project_id, category_id)
```

**태그 방식이므로 복수 지정이 가능하다.** *"교육 + 예약"* 같은 조합이 자연스럽다.
**축별 1개 제한을 두지 않는다** — 제한하면 단일 목록으로 만든 이점이 사라진다.

| 위치 | 표기 |
|---|---|
| `C-01` 카드 | **최대 2개.** `category.sort_order` 앞선 것부터 |
| `P-04` 상세 | **전부** |
| `A-03` 관리자 | 다중 선택. **`axis`로 묶어서 표시** |

> **`ON DELETE RESTRICT`** — 사용 중인 분류를 지우면 프로젝트의 태그가 사라진다.
> 연결을 먼저 정리하도록 강제한다.

> **v1은 필터가 없다** (A-4). 분류는 **표기용**이며 필터 도입은 2차다.

### 3.6 `course` — 교육 과정

| 컬럼 | 타입 | NULL | 기본값 | 제약 |
|---|---|:---:|---|---|
| `slug` | `text` | ✕ | | **UNIQUE.** 관리 화면 식별용 — v3.3에서 P-08 폐지로 공개 경로는 없어졌다 |
| `title` | `text` | ✕ | | |
| `description` | `text` | ○ | | |
| `curriculum` | `jsonb` | ✕ | `'[]'` | 커리큘럼 항목 배열. P-07 카드를 펼쳤을 때 렌더한다 |
| `status` | `text` | ✕ | `'preparing'` | `open` / `preparing` |
| `is_public` | `boolean` | ✕ | `false` | |
| `sort_order` | `int` | ✕ | `0` | |
| `meta_*` | `text` | ○ | | |

**`status = preparing`이면 렌더하지 않는다** (`03 §4.6`).
D-2 결정에 따라 **콘텐츠 미수령 시 전체를 숨긴다.**

> **v3.3 — P-08(교육 과정 상세) 폐지.** `curriculum` 필드를 소비하던 화면이 P-08에서
> P-07 카드 펼침으로 바뀌었을 뿐, 필드 자체는 계속 쓰인다. `slug`도 공개 라우팅 용도는
> 없어졌지만 관리 화면에서 항목을 식별하는 데 여전히 필요하므로 컬럼 삭제는 하지 않는다.
> 결정시트 `I-1` 참조.

### 3.6a `insight` — 인사이트 글 *(v3.1 신설)*

| 컬럼 | 타입 | NULL | 기본값 | 제약 |
|---|---|:---:|---|---|
| `slug` | `text` | ✕ | | **UNIQUE.** 고유 경로 (`REQ-F-092`). **예약어 3종 금지** |
| `title` | `text` | ✕ | | |
| `body` | `text` | ✕ | | 본문. 발주사가 작성 |
| `category` | `text` | ✕ | | `before` / `process` / `people` |
| `builder_id` | `uuid` | ✕ | | FK → `builder(id)`. 작성 빌더 (`REQ-F-095`) |
| `cover_image_url` | `text` | ○ | | **본문 첫 이미지에서 파생 저장** (`REQ-F-094`) |
| `status` | `text` | ✕ | `'draft'` | `draft` / `review` / `published` |
| `published_at` | `timestamptz` | ○ | | 발행 시각. 목록 정렬 기준 |
| `meta_*` | `text` | ○ | | POL-06 적용 |

**예약어 제약** — `slug` 는 `before` · `process` · `people` 이 될 수 없다. 카테고리 경로와 같은 계층을 쓰기 때문이다(`02 §4` 예약어 규칙). DB 레벨 `CHECK` 제약과 A-07 입력 검증(`FN-A07-04`) 양쪽에 둔다.

```sql
CONSTRAINT insight_slug_not_reserved
  CHECK (slug NOT IN ('before', 'process', 'people'))
```

**`builder_id` 를 NOT NULL 로 둔 이유** — `REQ-F-095`가 익명·조직 명의 글을 금지한다. NULL 을 허용하면 익명 글이 만들어질 수 있다.

**`cover_image_url` 은 파생 값이지만 저장한다.** §6의 "파생 값은 저장하지 않는다" 원칙의 예외다 — 본문에서 첫 이미지를 매번 파싱하면 목록 렌더 비용이 커지고, OG 태그는 SSR 시점에 확정돼야 한다. 저장 시점은 본문 저장 시이며, 본문이 바뀌면 함께 갱신한다.

**`status = published` 이고 `published_at` 이 있어야 공개된다.** 그 외 상태는 렌더하지 않고 직접 접근 시 404다.

### 3.7 `admin_user` — 운영팀 계정

| 컬럼 | 타입 | NULL | 제약 |
|---|---|:---:|---|
| `auth_user_id` | `uuid` | ✕ | FK → `auth.users(id)`. **UNIQUE** |
| `name` | `text` | ○ | 표시용 |

**관리자 계정은 복수다** (A-1). 이 테이블에 행이 있으면 `admin` 역할이다.

> **역할을 별도 컬럼이 아니라 테이블 소속으로 판정한다.** `builder`에 있으면 빌더,
> `admin_user`에 있으면 관리자다. RLS 조건이 단순해진다.

## 4. RLS 정책

**`REQ-N-011`을 만족하는 핵심이다.** 프론트가 아니라 DB가 막는다.

### 4.1 판정 함수

```sql
create function is_admin() returns boolean as $$
  select exists (select 1 from admin_user where auth_user_id = auth.uid());
$$ language sql security definer stable;

create function my_builder_id() returns uuid as $$
  select id from builder where auth_user_id = auth.uid();
$$ language sql security definer stable;
```

### 4.2 정책 표

| 테이블 | 동작 | admin | builder | 익명 |
|---|---|:---:|---|:---:|
| `builder` | SELECT | 전체 | 전체 | **`is_public` 만** |
| | UPDATE | 전체 | **본인 행.** 단 `slug` · `cohort` · `is_public` · `is_pinned` · `pin_order` 제외 | ✕ |
| | INSERT · DELETE | ○ | ✕ | ✕ |
| `project` | SELECT | 전체 | 전체 | **`is_public` 만** |
| | UPDATE | 전체 | **`is_owner`인 건만.** `slug` · `is_public` · `sort_order` 제외 | ✕ |
| | INSERT · DELETE | ○ | ✕ | ✕ |
| `project_builder` | ALL | ○ | **SELECT만** | ✕ |
| `project_category` | ALL | ○ | **SELECT만** | 공개 프로젝트분 |
| `category` · `course` | SELECT | 전체 | 전체 | `is_public` 만 |
| | 그 외 | ○ | ✕ | ✕ |
| **`insight`** *(v3.1)* | SELECT | 전체 | 전체 | **`status = 'published'` 만** |
| | INSERT · UPDATE · DELETE | ○ | **✕** | ✕ |

> **`insight` 쓰기를 관리자로만 제한한 이유** — 발행이 곧 대외 콘텐츠가 되므로 2단 권한(A-1)의 범위를 넓히는 결정이 필요하다. `FN-A07-10`과 같은 판단이며 **좁게 시작**한다. 빌더 작성으로 넓힐 때는 `project` 의 `is_owner` 패턴을 그대로 쓰면 된다 — `builder_id = my_builder_id()` 한 줄이다. **발주사 확인 필요.**

**빌더의 UPDATE 예시**

```sql
create policy builder_update_own on project
for update to authenticated
using (
  exists (
    select 1 from project_builder pb
    where pb.project_id = project.id
      and pb.builder_id = my_builder_id()
      and pb.is_owner              -- ← G-3b. 이 줄만 지우면 전원 편집으로 전환
  )
);
```

> **G-3b를 나중에 완화하기 쉬운 이유가 여기 있다.** `and pb.is_owner` 한 줄이다.

### 4.3 컬럼 단위 제한

**Postgres RLS는 행 단위다.** 특정 컬럼만 막으려면 둘 중 하나를 쓴다.

| 방법 | 판단 |
|---|---|
| `GRANT UPDATE (컬럼목록)` | **권장.** DB가 강제 |
| 서버 액션에서 필드 필터링 | 보조 |

**둘 다 적용한다.** `REQ-N-011`이 *"프론트엔드 은닉으로 대체하지 않는다"*를 요구하므로
**DB 권한이 1차 방어**이고 서버 액션이 2차다.

## 6. 파생 값 — 저장하지 않는다

| 값 | 계산 |
|---|---|
| 빌더의 프로젝트 수 | `project_builder` 조인 후 `is_public` 필터. **공동 건 포함** (G-3d) |
| 프로젝트 본문 글자 수 | 네 `body_*` 컬럼 합계 |
| 담당 빌더 표기 | 대표 + `count - 1`로 *"OOO 외 N명"* 구성 |

**집계 컬럼을 두지 않는다.** 공개 상태가 바뀔 때마다 갱신해야 하고 불일치가 생긴다.

## 7. 정렬 구현

### 7.1 빌더 목록 — 일별 시드 랜덤

```
1. is_pinned = true  → pin_order 순
2. 나머지            → 당일 날짜를 시드로 셔플
3. 하루 단위 캐싱
```

**셔플은 DB가 아니라 애플리케이션에서 한다.**
날짜 문자열(`YYYY-MM-DD`)을 시드로 쓰는 결정적 셔플이면 **같은 날 같은 순서**가 보장된다.

> `order by random()`을 쓰면 요청마다 순서가 바뀌어 `REQ-F-020`의
> *"동일 날짜 내 순서 동일"*을 만족하지 못한다.

### 7.2 프로젝트 목록

`sort_order` 오름차순 → 동일 시 `created_at` 내림차순.
