## 1. 개요

### 1.1 목적

본 문서는 AI 빌더 그룹 랜딩 페이지 구축 프로젝트에서 구현해야 할 요구사항을 정의한다. 기능 요구사항, 비기능 요구사항, 제약 사항을 식별하고 우선순위와 검수 기준을 명시하여 설계·개발·검수의 기준을 제공한다.

### 1.2 적용 범위

본 문서는 프로젝트 전 단계에 적용되며, 범위 판정의 기준선이 된다.

> 외주 프로세스 매뉴얼 §03 — *"기획 단계에서 확정된 화면 수, 기능 수가 이후 추가 요청의 기준선이 됩니다."*
> 외주 프로세스 매뉴얼 §07 — *"범위 내/외를 판정한다. 기준은 컨펌받은 기획 산출물입니다."*

본 문서에 정의되지 않은 요구는 범위 외로 간주하며, 추가 시 범위 변경 절차를 따른다.

## 2. 시스템 개요

### 2.1 시스템 목적

바이브코딩 외주를 검토하는 발주자가 유입 → 신뢰 확인 → 문의의 흐름으로 전환되는 웹사이트를 구축한다. 본 시스템의 1차 목적은 리드 수집이며, 결제 및 계약은 사이트 외부(영업 프로세스)에서 이루어진다.

발주자가 경쟁사와 발주사를 구분하지 못하는 것이 해결 대상 문제이며, 포트폴리오 · 교육 · 일하는 방식 세 축의 증거를 통해 이를 해소한다.

### 2.2 사용자 정의

| 구분 | 사용자 | 주요 행위 |
|---|---|---|
| 1차 | 발주자 (외부) | 웹/앱·플랫폼 외주를 검토하는 스타트업 대표 · 사업 담당자. 콘텐츠와 결과물을 확인하고 문의 제출 |
| 2차 | 영업팀 (내부) | 수집된 리드를 확인하고 적합한 빌더 프로필을 발주자에게 송부 |
| 3차 | 콘텐츠 관리자 · 빌더 (내부) | 포트폴리오 · 교육 콘텐츠 등록 및 관리 |

1차 사용자 특성

| 항목 | 내용 |
|---|---|
| 예산 규모 | 수백만 ~ 수천만 원 |
| 의사결정 | 사이트에서 즉시 결정하지 않음. 복수 업체를 비교 |
| 판단 근거 | 로고·수치가 아닌 일하는 방식과 실제 결과물 |

### 2.3 시스템 구성

| 관리 영역 | 인증 · 빌더 관리 · 프로젝트 관리 · 교육 과정 관리 · **빌더 개인 관리** |
| 외부 연동 | 플러그(문의 폼·CRM) · GA4 · GTM · 구글 서치콘솔 · 네이버 서치어드바이저 |

### 2.4 차별화 소구점

발주사가 리서치 과제로 지정한 사항의 결과다. 경쟁 개발사 4곳을 세 축 기준으로 분석하여 도출했다. 분석 원본은 『요구사항 정의서 상세』 §1.12를 참조한다.

| TenAI | 없음 | 없음 | 없음 |
| 세컨팀 | 자사 제품 UI만 | 없음 | 6단계 여정 공개 |

| DevTeam Korea | 익명 텍스트 사례만 | 없음 | 없음 |

| 관찰 | 내용 |
|---|---|
| 공백 1 | 4곳 중 결과물 링크와 담당자를 동시에 제공하는 곳이 없다 |

#### 구조 서술 카피의 허용 범위 (v3.0 신설)

위 경쟁사 비교표의 축은 결과물 검증 · 인력 실체 · 일하는 방식 세 가지다. **교육 축은 비교 대상에조차 없다** — 4곳 중 인력을 직접 교육해 투입하는 곳이 없기 때문이다. 이는 표에 명시되지 않은 네 번째 공백이며, REQ-F-032가 요구하는 "교육 → 실무 투입 → 매니징의 인과"와 정확히 대응한다.

따라서 **"교육받은 사람이 만들고, 조직이 책임진다"는 서술은 소구점에 없는 새 주장이 아니라 REQ-F-032의 압축**이므로 카피로 사용할 수 있다. 단 위 표의 수치 · 경쟁사 언급 · 가격 규칙은 그대로 적용되며, 추가로 **비교급·최상급("유일한 · 최초의 · 최고의")을 사용하지 않는다.** 구조 서술은 비교 우위 선언이 아니라 자사 구조의 기술이다. 세부 조건은 POL-13 §카테고리 선점 카피의 허용 조건.

주의 — 소구점 3의 근거인 관리 도구 화면은 실데이터 축적 후에만 사용 가능하다 (POL-09 촬영 조건).

#### 인사이트 판정 정정 (v3.1)

종전 판정은 *"본문이 발주사 담당 범위이며 빈 상태 배포를 감수할 수 없다"* 였다. 이는 발주사가 면제한 **본문 텍스트 작성**을 **화면 자체의 범위 제외**로 확대 해석한 것이다. 근거 발언은 다음과 같다.

> (06:11) "저희는 콘텐츠로 이런 포트폴리오를 콘텐츠로 담았고 그리고 **인사이트는 여기는 이제 블로그예요.** … 기본적으로 **블로그를 작성할 수 있는 어드민 페이지도 있지만 작성뿐만 아니라 SEO geo에 최적화될 수 있는 환경으로 세팅을 해놨어요.**"

> (22:04) "블로그에 들어가는 콘텐츠들 … **이런 것들은 클라이언트의 몫이거든요.** 이거를 어떻게 쓸지까지는 생각 안 하셔도 돼요. 근데 이제 눌렀을 때 이렇게 링크로 **슬러그**로 잡히고 요게 여기 안에서 **첫 번째 이미지가 이제 썸네일로 잡히는 것들** … 이런 것들의 세팅이 잘 돼 있어야 돼."

발주사가 면제한 것은 본문 작성이며, 어드민·슬러그·OG 썸네일·SEO 환경은 **명시적 요구 사항**이다. 따라서 범위 변경이 아니라 **판정 정정**으로 처리한다. 상세는 『녹취록 대조 재감사』 F-1.

**남은 우려 — 빈 상태 배포.** 종전 판정이 지적한 "납품 시점에 본문이 없다"는 문제는 정정 후에도 유효하다. 본문 확보를 납품 조건으로 삼지 않되, 빈 목록에 대응하는 문구를 REQ-F-090에 포함한다.

> GEO 대응은 유지된다. FAQ는 보강 수단이었고, `P-04`(색인 우선순위 1위)와 테크니컬 SEO(REQ-F-070대)가 본 수단이다.

정렬 방식 — 일별 시드 랜덤

날짜를 시드로 사용하여 하루 단위로 순서를 고정한다. 매 요청 셔플과 고정 정렬의 중간 방식이다.

| 요건 | 충족 방식 |
|---|---|
| 노출 균등성 | 매일 순서가 변경되어 특정 빌더의 상단 점유가 발생하지 않는다 |
| 정적 생성 호환 | 하루 단위로 순서가 고정되므로 캐싱이 가능하다 (일 1회 재생성) |
| 재방문 탐색 | 동일 날짜 내에서는 순서가 유지되어 이전에 확인한 빌더를 다시 찾을 수 있다 |
| 검수 재현성 | 동일 날짜에 동일 화면이 재현된다 |

**기수별 그룹핑을 두지 않는다.** 기수는 발주자에게 의미가 없는 내부 개념이며, 그룹을 두면 그룹 간 순서를 결정해야 하는 문제가 발생한다. 기수 정보는 카드 배지로만 노출한다(REQ-F-020b).

확장성 요구 — 빌더는 기수 단위로 증감한다. 1기 12명 기준으로 설계하지 않고 목록 구조로 취급하여, 인원 변동 시 레이아웃 재설계가 불필요하도록 한다.

| 규모 | 처리 방식 |
|---|---|
| ~50명 | 단일 목록 + 카드 그리드, 일별 시드 랜덤 |

REQ-F-056 신설 사유 (v3.0) — 전환 온도차 설계(즉시 전환 의사가 없는 방문자를 위한 저마찰 경로)는 일반적으로 보조 CTA를 병행해 구현하나, **REQ-F-007이 경쟁 CTA를 금지**하므로 이 방식을 쓸 수 없다. 대신 클릭 대상이 아닌 **텍스트 마이크로카피**로 같은 효과를 얻는다. 링크화하면 REQ-F-007 위반이 되므로 검수 항목에 앵커 태그 부재를 포함한다.

### 4.11 본문 작성 가이드 (4문항)

500자 요건을 달성 가능하게 만드는 장치다. 백지 상태에서는 달성이 어려우나 질문에 답하는 형식이면 자연히 충족된다.

| # | 문항 (h2 소제목) | 분량 |
|:---:|---|---|
| 1 | 무엇을 만들었나 | 2~3문장 |
| 2 | 왜 필요했나 (문제) | 2~3문장 |
| 3 | 어떻게 풀었나 | 3~4문장 |
| 4 | 결과 | 1~2문장 |

적용 결과 500~700자가 산출된다. 최소값을 800자가 아닌 500자로 설정한 근거이며, 기수마다 신규 인원이 반복 충족해야 하므로 달성 가능한 기준을 채택했다.

동일 구조가 세 계층에서 작동한다.

| 계층 | 역할 | 관련 요구사항 |
|---|---|---|
| 관리자 입력 | 편집기 기본값 | REQ-F-065 |
| 페이지 구조 | 상세 페이지 h2 소제목 | REQ-F-013 |
| GEO | 질문형 소제목 + 2~3줄 문단 = 인용 단위 | REQ-F-078 |

4번째 문항은 "결과"로 통일한다. 유형별로 분기하지 않는다.

| 근거 | 내용 |
|---|---|
| 독자 관점 | 발주자는 학습 과정이 아닌 성과를 확인한다 |
| 진열 일관성 | 두 출처가 동일 목록·동일 카드 컴포넌트를 사용한다 |
| **구분 표기 부재** | **실전/제작물 구분을 노출하지 않으므로 소제목으로 구분이 드러나면 안 된다** |

작성 주체 — 본문은 빌더 본인이 작성한다. 팀은 문장 정리와 SEO 메타 입력을 담당한다. 단, 실전 사례 4건은 빌더가 작성할 수 없으므로 발주사 제공 자료를 기반으로 팀이 작성한다.

발주사가 답을 제시하지 않고 리서치를 요청한 항목이다. 요구사항이 아니므로 REQ 번호를 부여하지 않되, 착수 전 산출물이 존재해야 한다.

> 과제 A의 "실제와 다를 수 있어도 소구할 수 있는 요소"는 없는 실적을 창출하라는 의미가 아니다. 동일 미팅에서 "실제 데이터가 들어가야 한다"를 함께 요구했다. 소구 요소를 발굴하되 사실은 정확하게 기술한다.
