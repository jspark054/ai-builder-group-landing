## 1. 개요

### 1.1 목적

『기능 명세』가 무엇이 어떻게 동작하는가를 정의한다면, 본 문서는 경계 조건에서 어떻게 판정하는가를 정의한다.

데이터가 없을 때, 값이 0일 때, 형식이 어긋날 때, 판단이 갈릴 때 적용하는 규칙이다. 설계·개발·검수 시 판단이 필요한 지점에서 본 문서를 기준으로 결정한다.

### 1.2 적용 원칙

| 원칙 | 내용 |
|---|---|
| 우선 적용 | 정책과 기능 명세가 충돌하면 정책이 우선한다 |
| 판정 가능성 | 모든 정책은 참·거짓으로 판정 가능해야 한다. "적절히", "잘" 같은 표현을 사용하지 않는다 |
| 근거 구분 | 발주사 요구와 팀 판단을 구분 표기한다. **팀 판단 항목은 반려 사유로 사용하지 않는다** |

### 1.3 참조 문서

| 문서명 | 문서 번호 | 관계 |
|---|---|---|
| 요구사항 정의서 | ABG-REQ-001 | 상위 |
| 요구사항 정의서 상세 | ABG-REQ-001-A | 근거 |
| 화면 목록 (IA) | ABG-IA-002 | 동급 |
| 기능 명세 | ABG-FN-003 | 동급 |
| 화면 설계 (와이어프레임) | ABG-WF-005 | 하위 — 미작성 |

### 표기 규칙 (문서 공통)

| 표기 | 용도 |
|---|---|
| **굵게** | **판정 · 금지 조건에만 사용한다.** "~하지 않는다", "~시 불합격", "미노출", "차단" |
| `코드` | 수치 · 등급 · 경로 · 속성값 |
| 평문 | 그 외 전부 |

굵게 표시된 문장은 **검수 시 판정 대상**이다. 강조 목적으로 사용하지 않는다.

### 1.4 근거 유형 표기

| 표기 | 정의 |
|---|---|
| 요구 | 발주사가 명시적으로 요청한 사항. 임의 변경 불가 |
| 매뉴얼 | 외주 프로세스 매뉴얼 명문 조항 |
| 실측 | 직접 확인하여 검증한 결과 |
| 팀 | 팀 리서치 및 판단. **반려 사유로 사용하지 않는다** |

## 3. 콘텐츠 정책

### POL-01 · 수치 노출 금지

근거 요구 · 녹취록 20:34

**실제 값이 없는 수치를 화면에 노출하지 않는다.**

| 상태 | 처리 |
|---|---|
| 값이 존재한다 | 노출한다. 카운트업 애니메이션 허용 |
| 값이 0이거나 미확정이다 | **해당 요소를 렌더하지 않는다** |

적용 대상

| 대상 | 처리 |
|---|---|
| 교육 섹션 누적 수치 (기수 · 수료 인원) | 1기 진행 중이므로 **v1에서 수치 소구를 사용하지 않는다** |
| 관리 도구 화면 캡처 | 비용 · 호출 · 이슈 수치가 0인 상태로 노출 불가. §POL-09 촬영 조건 참조 |
| 프로젝트 성과 지표 | 측정 근거가 없는 수치를 기재하지 않는다 |

판정 기준 — 화면에 노출된 모든 수치에 대해 실제 데이터 출처를 제시할 수 있어야 한다. **값이 0인 수치가 하나라도 노출되면 불합격이다.**

> 경쟁사 분석에서 확인된 대표적 실패 사례가 값 0인 통계 카운터의 노출이다. 신뢰를 얻으려는 요소가 오히려 신뢰를 훼손한다. 대신 실물(라이브 링크)로 신뢰를 확보한다.

### POL-03 · 링크 검증력 등급

근거 팀

프로젝트 결과물의 접근 가능성을 5단계로 구분하고, 등급에 따라 표기를 달리한다.

| 등급 | 형태 | 카드 표기 | 검증력 |
|---|---|---|---|
| `live` | 운영 중인 서비스 | 바로가기 | 최상 |
| `deploy` | 배포된 결과물 | 바로가기 | 상 |
| `repo` | 코드 저장소 | 코드 보기 | 중 |
| `video` | 동작 영상 | 동작 영상 | 하 |
| `none` | 없음 | **버튼 미노출** | — |

소구 성립 기준 — `deploy` 등급까지는 "실제로 만들었다"는 소구가 성립한다.

등급별 처리

| 상황 | 처리 |
|---|---|
| `none` 등급 | **바로가기 버튼만 미노출.** 콘텐츠·이미지·상세 진입 링크는 정상 노출 |
| 링크 유효성 | 등록 시 형식 검증만 수행한다. 응답 확인은 수동 |
| 링크 사망 발견 시 | 관리 화면에서 등급을 `none` 또는 `video`로 즉시 변경한다 |
| 자동 헬스체크 | 2차 범위. v1에서는 구현하지 않되 즉시 내릴 수 있는 경로는 확보한다 |

> 사망한 링크는 없는 것보다 해롭다. 열었을 때 404가 나오면 스크린샷만 있는 경우보다 신뢰가 크게 훼손된다.

주의 — `none` 등급이어도 상세 진입 링크는 유지한다. 이를 함께 제거하면 해당 프로젝트가 색인 대상에서 완전히 제외된다.

### POL-04 · 콘텐츠 최소 분량

근거 팀

| 항목 | 최소 | 권장 | 목적 |
|---|---|---|---|
| 프로젝트 요약 | 40자 | — | 카드에서 한 줄이 비지 않도록 |
| 프로젝트 본문 | 500자 | 800자 | 답변엔진 인용 가능 분량 확보 |
| 빌더 소개 | 30자 | — | — |

본문 구조 — 4문항(무엇을 → 왜 → 어떻게 → 결과)을 h2 소제목으로 구성한다. 각 문단은 2~3줄 단위로 끊어 자기완결 블록을 만든다.

> 전체 분량 확보와 문단 길이 제한은 층위가 다른 요구다. 분량은 500자 이상이되, 문단은 짧게 유지한다. 긴 문단은 답변엔진이 인용 단위로 잘라내기 어렵다.

최소값 설정 근거 — 4문항에 답하면 자연히 500~700자가 산출된다. 800자가 아닌 500자로 설정한 이유는 기수마다 신규 인원이 반복 충족해야 하므로 달성 가능한 기준이어야 하기 때문이다.

분량 미달 처리

| 상황 | 처리 |
|---|---|
| 관리 화면 입력 중 | 실시간 카운터로 현재 글자 수를 표시하고 미달 시 경고한다 |
| 공개 전환 시 | 체크리스트 항목으로 확인한다 (POL-08). **경고하되 차단하지 않는다** |
| 검수 시 | **공개 상태 프로젝트 중 500자 미만이 존재하면 불합격이다** |


|:---:|---|

3개 조건 미충족 시 아키텍처 다이어그램으로 대체한다.

### POL-10 · 에셋 정책

근거 요구

| 대상 | 정책 |
|---|---|
| 포트폴리오 실화면 · 라이브 링크 | 실물 유지. 핵심 소구의 근거이므로 대체 불가 |
| 교육 · 배경 · 보조 이미지 | 무료 에셋 사용 허용 |

판단 기준은 출처가 아니라 완성도다. 품질이 낮은 실물보다 잘 선택된 무료 에셋이 낫다. 교육 촬영 에셋이 확보되면 그쪽을 우선한다.

#### 목업 이미지 사용 시점

| 시점 | 목업 |
|---|---|
| 최종 산출물 | **사용 금지.** 실화면으로 교체한다 |
| 제작 과정 (시안 · 중간 공유) | 사용 가능 — 특히 교육 콘텐츠 영역 |

교육 섹션은 촬영 에셋 수급이 지연될 수 있으므로 제작 과정에서 목업으로 자리를 확보하고 최종본에서 교체하는 흐름을 허용한다.

**단, 포트폴리오 실화면은 어느 시점에도 목업으로 대체하지 않는다.**

#### 이미지 생성

이미지 생성이 필요한 경우 별도 도구를 사용한다. 생성 이미지에도 POL-01·POL-09가 동일 적용된다.

## 4. 표시 정책

### POL-02 · 빈 상태 처리

근거 팀

| 상황 | 처리 |
|---|---|
| 프로젝트 0건인 빌더 | **목록에 노출하지 않는다** |
| 빌더 이미지 미등록 | 폴백 표시 — 표기명 이니셜 또는 기본 그래픽 |
| 프로젝트 썸네일 미등록 | **등록 불가 처리.** 썸네일은 필수 항목 |
| 수료 빌더 0명인 과정 | 과정은 노출하되 빌더 목록 영역만 숨긴다 |
| 공개 프로젝트 0건 | 랜딩 포트폴리오 섹션을 숨긴다. 목록 화면은 빈 상태 안내 표시 |
| 공개 빌더 0건 | 랜딩 빌더 섹션을 숨긴다. 목록 화면은 빈 상태 안내 표시 |
| **발행 인사이트 0건** *(v3.1)* | **P-12를 숨기지 않는다.** 빈 상태 문구를 표시한다 — 「첫 글을 준비하고 있습니다.」 |
| **카테고리별 글 0건** *(v3.1)* | 카테고리 필터는 유지하고 「이 주제로 정리한 글이 아직 없습니다.」를 표시한다 |
| 인사이트 본문 이미지 없음 | OG 썸네일에 기본 이미지를 사용한다 (REQ-F-094) |

원칙 — 빈 카드나 값이 비어 있는 요소를 렌더하지 않는다. 요소를 숨기거나 폴백으로 대체한다.

> 프로젝트가 없는 빌더는 결과물 검증이라는 소구에 기여하지 못한다. 빈 카드는 POL-01과 동일한 문제를 만든다.
>
> **인사이트만 예외적으로 숨기지 않는다 (v3.1).** 다른 영역은 콘텐츠가 없으면 섹션을 숨기지만, 인사이트는 본문 작성이 발주사 담당이라 납품 시점에 0건일 수 있다. 화면을 숨기면 발주사가 글을 넣을 자리 자체를 확인할 수 없으므로, 빈 상태 문구로 대체한다. 요구사항 정의서 §3.3의 "빈 상태 배포" 우려에 대한 대응이다.

### POL-07 · 정렬 기준

근거 팀

| 목록 | 정렬 방식 |
|---|---|
| 빌더 목록 | 일별 시드 랜덤. 고정 지정 빌더는 셔플에서 제외하고 상단 배치 |
| 프로젝트 (랜딩 · 목록) | 수동 지정 순서 |
| 프로젝트 (빌더 상세) | 수동 지정 순서 → 동일 시 등록순 |
| 교육 과정 | 진행 중 우선 → 수동 지정 순서 |

#### 빌더 목록 정렬 상세

```
1. 고정 지정 빌더 → 지정 순서대로 상단 배치
2. 나머지 빌더    → 당일 날짜를 시드로 셔플
3. 결과를 하루 단위로 캐싱
```

| 요건 | 충족 방식 |
|---|---|
| 노출 균등성 | 매일 순서가 변경되어 특정 빌더의 상단 점유가 발생하지 않는다 |
| 정적 생성 호환 | 하루 단위 고정이므로 캐싱이 가능하다 |
| 재방문 탐색 | 동일 날짜 내 순서 유지로 이전 확인 빌더를 다시 찾을 수 있다 |
| 검수 재현성 | 동일 날짜에 동일 화면이 재현된다 |

**기수별 그룹핑을 두지 않는다.** 기수는 카드 배지로만 표시한다.

#### 자동 정렬을 사용하지 않는 이유

최신순 · 조회순 등 자동 정렬은 품질 편차를 그대로 노출한다. 빌더가 각자 콘텐츠를 등록하는 구조이므로 편차가 발생하며, 운영팀이 노출 순서에 개입할 수 있어야 한다.

조회순 정렬은 데이터가 축적된 후 2차에서 검토한다.

### POL-13 · 카피 작성 및 확정

> **v3.4 — 개발 단계 카피는 확정이 아니다.** "카피 초안 작성 → 수행사"의 결과물(기획문서

> 그대로 유지된다 — 팀원이 무엇을 쓰든 게시 전에는 여전히 발주사 컨펌을 거친다. 결정시트
> `I-7` 참조.

근거 요구

| 단계 | 주체 | 근거 |
|---|---|---|
| 카피 초안 작성 | 수행사 | 랜딩 카피는 SEO 키워드 · 타이틀 15자 · 정보구조와 결합되어 있다 |
| AI 생성분 교정 | 수행사 | AI 자동 생성 워딩은 품질이 저하된다 |
| 최종 확정 | 발주사 | 사이트의 주인이며, 매뉴얼 §03의 단계별 컨펌이 그 절차다 |
| 블로그 · 인사이트 본문 | 발주사 | 명시적 요구 |

시안 단계에서는 자리표시용 문안을 사용하고 최종본에서 교체한다.

카피 초안은 『요구사항 정의서』 §2.4의 확정 소구점 3건을 근거로 작성한다. 소구점에 없는 주장을 카피로 만들지 않는다.

**별도 승인 프로세스를 구성하지 않는다.** 매뉴얼의 검수보고서 및 컨펌 관문에 카피를 포함시킨다.

#### 카테고리 선점 카피의 허용 조건 (v3.0 신설)

"교육받은 사람이 만들고, 조직이 책임진다"와 같이 **자사의 구조를 정의하는 카피**는 소구점에 없는 새 주장이 아니라 REQ-F-032("교육 → 실무 투입 → 매니징의 인과를 보여주는 신뢰 근거로 구성한다")를 압축한 것이므로 허용한다. 단 아래 세 조건을 모두 만족해야 한다.

| # | 조건 | 근거 |
|:---:|---|---|
| 1 | **비교급·최상급을 쓰지 않는다.** "유일한 · 최초의 · 최고의" 불가 | POL-13 과장 부사 금지 |
| 2 | **경쟁사를 지시하지 않는다.** "타사와 달리 · 다른 곳과 다르게" 불가 | REQ-F-005 |
| 3 | **수치를 근거로 삼지 않는다.** "국내 1위 · 수료생 N명" 불가 | POL-01 |

즉 카테고리 선점은 **비교 우위 선언이 아니라 자사 구조의 서술**로만 구현한다. "우리가 제일 낫다"가 아니라 "우리는 이렇게 일한다"를 말하는 것이다.

**착지 조건** — 구조를 주장하는 카피는 같은 페이지 안에서 근거로 착지해야 한다. 교육 축을 주장하는 카피는 P-07(교육 페이지, P-08은 v3.2에서 폐지)이 아니라 **P-06 빌더 이력과 FN-P09-04 역할 분리 조직**에 착지시킨다. 안건 8(교육 라인업 공개 시점)이 미확정이어도 주장이 근거를 잃지 않게 하기 위함이다.

#### 톤앤매너 (v3.0 개정 — 4단 레지스터)

기본 문체를 **격식체("~하세요 / ~니다")로 한다.** 외주 개발은 신뢰가 구매 요인이므로, 가벼운 구어체보다 격식체가 소구점(검증 가능한 결과물 · 거버넌스 공개)과 일관된다.

v2.0까지의 "친근체('~해요') 기본" 정책은 폐기하지 않고 **레지스터 R1로 흡수한다.** 친근한 구어의 질감은 발주사의 목소리를 인용하는 구간이 담당하고, 브랜드가 말할 때는 격식체를 지킨다.

전환 원칙 — **말하는 주체가 바뀔 때만 어미가 바뀐다.**

| 레지스터 | 말하는 주체 | 어미 | 사용처 | 예시 |
|:---:|---|---|---|---|
| **R1 인용** | 발주사(고객)의 속마음 | 구어체 평서 — **인용부호 필수** | 문제 제기 · 선택 기준 헤드 | "누가 만들지도 모르고 맡기라고요?" |
| **R2 공감** | 브랜드(부드럽게) | "~습니다" · 완충 어휘 | 문제 진단 본문 | "캡처 화면은 어디나 그럴듯합니다." |
| **R3 단언** | 브랜드(근거 제시) | "~니다" · 단정형 | 소구점 · 프로세스 · 조직 | "교육받은 사람이 만들고, 조직이 책임집니다." |
| **R4 권유** | 브랜드 → 사용자 | "~하세요 / ~해보세요" | CTA · 확인 요청 | "지금 바로 열어볼 수 있는 실제 서비스로 확인해보세요." |

**검수 규칙** — R1은 반드시 인용부호 안에만 존재한다. 인용부호 밖에서 구어체가 나오면 격식체 원칙 위반으로 간주하고 R2/R3로 되돌린다.

> **v3.2 완화** — "네 레지스터 외의 혼용은 불합격 사유다"라는 강제 규정은 폐기한다.
> 시안 비교로 방향성(확정 소구점 · 톤)이 클라이언트에게 충분히 검증됐으므로, R1~R4
> 구분은 이제 **불합격 판정 기준이 아니라 작성 가이드라인**이다. 화면을 맡은 팀원이
> 자기 스타일로 표현을 조정할 수 있다. 단 R1(인용부호 필수)처럼 사실관계·형식과
> 연결된 규칙은 계속 지킨다. 결정시트 `I-5` 참조.

| 항목 | 정책 |
|---|---|
| 문체 | **격식체 기본**(R2~R4). 구어체는 인용부호 안(R1)에서만 허용 |
| 표현 | "무조건 가능합니다" 대신 가능 범위와 조건을 기술한다 |
| 주어 | **AI를 주어로 사용하지 않는다.** 사람이 판단하고 AI가 속도를 높인다고 기술한다 |
| 금지 | 이모지 · 과장 부사 · 공포 마케팅 |

| 5 | 통계 카운터가 데이터와 미연결 | POL-01로 별도 규정 |

| 8 | 보라 · 인디고 그라디언트 및 글로우 | 브랜드 색 의도적 선정 |

#### 디자인 레퍼런스

발주사 제공 레퍼런스는 참고 자료다. 합격·불합격을 가르는 기준선이 아니며, 톤과 패턴을 파악하는 용도로 사용한다.

> 레퍼런스 분석은 착수의 선행 조건이 아니다. ①항목 4개가 실질 판정 기준이며, 레퍼런스는 그 방향을 잡는 데 사용한다.

레퍼런스는 요청 시 제공된다. 필요하면 발주사에 요청한다.

#### 판정 방법

| 대상 | 방법 |
|---|---|
| 자사 제작 화면 | ①항목 4개 전수 확인. **하나라도 해당하면 불합격** |
| 포트폴리오 선별 | 동일 기준으로 빌더 기존 작업물을 판정하여 선별한다 |

## 8. 미결 사항

**v1.0의 안건 6건 중 5건이 확정되어 각 정책에 반영됐다.**

| 안건 | 항목 | 결정 | 정책 반영 |
|:---:|---|---|---|
| 1 | 관리자 권한 구조 | **2단 역할** | **POL-08 공개 토글은 관리자 전용.** 별도 승인 워크플로를 두지 않는다 |
| 5 | 포트폴리오 목록 분리 | **분류축 교체** | POL-07 정렬은 단일 목록 기준. 분류는 표기용 |
| 7 | 빌더 표기 동의 | **전원 동의** | **POL-12 적용 가능.** 표기 수위는 개인 선택으로 유지 |
| 8 | 교육 라인업 공개 시점 | **목업 진행 · 미수령 시 숨김** | POL-02 준비 중 과정은 렌더하지 않음 |
| 10 | 문의 출처 추적 | 미결 | 정책 영향 없음 |

### 8.1 남은 미결 — 1건

| 안건 | 항목 | 정책 영향 | 결정 전 처리 |
|:---:|---|---|---|
| 9 | 이관 정책 대외 공개 | POL-09 공개 범위 | **비공개.** P2이며 `P-09` 문단 유무 |

**v1.0에서 지적한 위험이 해소됐다.** 당시 *"안건 7이 결정되지 않으면 빌더 목록이 비어 있는 상태로 배포된다"*고 기술했으나, **전원 동의로 P-05·P-06이 성립한다.**

### 8.2 콘텐츠 수급이 새 위험이다

동의 문제는 풀렸으나 **실제 콘텐츠 입력은 별개다.**

| 완료 기준 | 요구 |
|---|---|
| 22번 | 세 축 콘텐츠가 전부 실데이터로 채워졌다 (**더미 0건**) |
| POL-11 ③ | 더미 목업 · 가짜 데이터는 **반려 사유** |

빌더 12명이 각자 프로필과 프로젝트 본문(최소 500자)을 작성해야 한다.
**관리 화면(A-02·A-03) 완성 직후 수집을 시작한다.** 개발 완료 후로 미루면 배포 게이트에서 막힌다.
