> 이 문서는 **기획안(전략·경쟁분석·근거)을 실행 단위로 번역**한 것이다. 전략적 배경은 기획안을, 원문 근거는 회의록·Q&A·매뉴얼을 참조한다.

## 1. 개요

**무엇을 만드는가** — 바이브코딩 외주를 맡기려는 발주자가 유입 → 신뢰 확인 → 문의로 전환되는 랜딩 페이지 1종(하위 페이지 포함 멀티 페이지 사이트).

**왜 만드는가** — 클라이언트는 실력 있는 개발사와 껍데기 포트폴리오를 구분하지 못한다. 이 문제를 **포트폴리오·교육·일하는 방식** 세 축의 증거로 해결한다.

**한 줄 포지셔닝** — 검증된 바이브코더를, 조직이 보증해서 붙여준다. 업체처럼 실체를 감추지 않고, 개인처럼 혼자 두지 않는다.

## 2. 목표 및 성공 지표

**비즈니스 목표** — 리드 수집(외주 문의 전환)이 1차 목적. 사이트는 결제 지점이 아니라 접점이며, 리드 → 영업팀 전화 → 프로젝트 배정으로 이어진다. 교육생 실무 배정은 장기 목표.

| 지표 | 정의 | 상태 |
|---|---|---|
| 문의 폼 제출 수 | 플러그 연동 폼 제출 건수 (1차 전환) | 계측 가능 |
| 포트폴리오 → 문의 전환율 | 어느 빌더/프로젝트를 보고 문의했는지 | TBD — 파라미터 자체는 설계됨(FR-5.3), 플러그 수신 지원 여부가 미확인이라 TBD (§7 FR-5.4) |
| `/ai` vs `/it` 세그먼트 비율 | 디폴트 포지셔닝 판단용 — 지표가 아니라 **의사결정 입력값** | 계측 가능 (§5 URL 구분) |
| 검색 노출 | 메인 키워드 순위, `site:도메인` 색인 현황 | SEO 6종 완료 후 측정 |
| 목표 정량치 | 문의 건수·순위 목표 | TBD — 대표와 합의 필요 |

**정성 성공 기준** — 매뉴얼 §11 종료 체크리스트 전부 통과 (§12 완료 기준).

## 3. 타겟 사용자

### 3.1 1차 — 발주자 (외부)

| 항목 | 내용 |
|---|---|
| 누구 | 웹/앱 외주를 맡기려는 스타트업 대표·사업 담당자 |
| 상태 | 똑개와 경쟁사(TenAI 등)를 **구분하지 못함** (클라이언트가 직접 정의한 타깃) |
| 예산 | 수백만~수천만 원. 대형 개발사는 예산이 안 맞고, 개인 프리랜서는 검증이 안 됨 |
| 행동 | 사이트에서 즉시 결정하지 않음. 여러 곳 비교하다 이탈하거나 문의를 남김 |
| 필요한 것 | "맡겨도 되는가"를 판단할 **근거** — 로고·수치가 아니라 일하는 방식과 실물 |

**여정** — 검색 유입 → 포트폴리오로 실력 확인 → 교육 이력으로 신뢰 보강 → 일하는 방식으로 리스크 안심 → 문의.

### 3.2 2차 — 영업팀 (내부)

리드가 들어오면 적합한 빌더를 골라 **그 프로필을 발주자에게 보내 피드백을 받는다.** → 빌더 프로필은 웹 페이지이자 영업 자료이며, **단독 URL 공유가 성립해야 한다** (§7 FR-5).

### 3.3 3차 — 콘텐츠 관리자·빌더 (내부)

포트폴리오·교육 콘텐츠를 등록한다. 권한 정책(통합 vs 개인별)은 미결이며 1차는 통합 관리자 권장 (§7 FR-7).

**2차 이해관계자** — 대표(서장원): 발주자이자 최종 컨펌 주체. 진행 중에는 사실상 클라이언트 역할.

## 4. 범위

### In Scope (v1, 3주)

- 랜딩 페이지 1종 + 하위 페이지(빌더/포트폴리오, 교육, 일하는 방식, 문의)
- 관리자(CMS): 통합 관리자 1계정으로 콘텐츠 등록
- 문의 폼(플러그 연동)
- SEO/GEO 테크니컬 세팅 6종
- 목업 → 실데이터 반영, Vercel 배포 → 똑개 계정 이관

### Out of Scope (v1)

| 항목 | 사유 |
|---|---|
| 블로그/인사이트 | 세 축(포트폴리오·교육·일하는 방식)에서 겉돌아 이번 범위 제외. 향후 2차로 구조만 확보 |
| 크루/커뮤니티(세미나·스터디) | 현재 1기 진행 중이라 실적 없음. 자리만 확보, 수료 후 2차 |
| 사이트 내 결제·견적 계산기 | 고가 외주라 전화 영업으로 전환. 리드 수집이 목적 |
| 발주자 회원가입·로그인 | 리드 폼으로 충분, 이탈 요인 |
| 빌더 개인별 CMS 권한 | "검토" 단계라 v1 확정 아님 — v2 후보 |
| 문의 데이터 자체 저장(inquiries) | 플러그 CRM이 담당 |
| AX 컨설팅 전용 콘텐츠 | 장기 확장. 지금은 바이브코딩 키워드 집중 |
| 다국어 | 언급 없음 |

## 5. 정보구조 (IA)

기획안 §5 기준. 경로명은 **[제안]**이며 디벨롭 단계에서 조정 가능.

```
/                     홈(랜딩) — 8개 섹션 (§7 FR-1)
/builders             빌더 목록                              [제안]
/builders/:name       빌더 상세 → 프로젝트 인라인 전개        [제안]
/portfolio/:slug      프로젝트 개별 URL (검색 진입점)         [제안]
/courses              교육 과정                              [제안]
/courses/:name        과정 상세 → 수료 빌더 목록             [제안]
/process              일하는 방식 (똑빌더/프로세스)          [제안]
/contact              문의 (플러그 폼 임베드)                [제안]
(/community)          커뮤니티 — 2차, 자리만 확보
```

**뎁스 원칙** — 빌더 상세에서 프로젝트가 클릭 없이 전부 보이고(1뎁스), `/portfolio/:slug`는 검색·AI 인용용 독립 진입점.

**canonical 미적용** — 빌더 페이지는 요약, 프로젝트 페이지는 전문으로 분량을 달리해 중복 자체를 만들지 않음.

**탭 URL 구분** — 교육 과정·포트폴리오 필터 등은 각각 고유 URL(`/courses/바이브코딩` 등). GA4 개별 페이지뷰·독립 색인·`/ai` vs `/it` 세그먼트 측정 목적.

## 6. 제품 원칙

기획안 §3-1의 Why③("왜 확인해 볼 게 없는가")에서 나온 세 질문을 그대로 원칙으로 옮겼다. 각 원칙은 §7 기능요구사항의 특정 FR로 실현된다.

| 원칙 | 문장 | 대응 축 (기획안 §3-2) |
|---|---|---|
| P-A | 실제로 만들 수 있다는 걸 보여준다 | 포트폴리오 |
| P-B | 실력이 어디서 왔는지 보여준다 | 교육 |
| P-C | 맡기면 어떻게 관리되는지 보여준다 | 일하는 방식 |

### 6-1. 원칙 → FR 매핑

각 원칙이 실제로 어느 FR에서 실현되는지 §7을 다시 읽고 확인했다. 결과물(콘텐츠)로 직접 드러나는 것은 **대응**, 그 원칙을 뒷받침하지만 간접적이거나 원칙의 일부만 해당하는 것은 **부분 대응**으로 표시했다. FR 내용은 새로 쓰지 않고 §7 원문을 그대로 참조한다.

#### P-A. 실제로 만들 수 있다는 걸 보여준다

| FR | 내용 요약 | 대응 정도 |
|---|---|---|
| FR-2.2 | 콘텐츠+실화면+라이브 링크 동시 노출 | 대응 |
| FR-2.3 | 데이터 소스 2층(실전 3건 + 빌더 13명×1건) | 대응 |
| FR-2.6 | 링크 등급(최상~최하) — 증거 강도 기준 | 대응 |
| FR-2.7 | 프로젝트 개별 URL — 독립적으로 검증 가능 | 대응 |
| FR-2.1 | 빌더→프로젝트 인라인 전개 뎁스 구조 | 부분 대응 — 증거에 접근하는 경로일 뿐, 증거 자체는 아님 |
| FR-2.4 | 선정 워크플로(리스트업→판정→대표 확인) | 부분 대응 — 증거가 진짜임을 보증하는 내부 절차, 화면에 드러나지 않음 |
| FR-2.5 | 'AI스럽지 않은' 페이지만 선별 | 부분 대응 — 증거의 신뢰도를 관리하는 필터, 증거 자체는 아님 |
| FR-2.8 | 카드 세부 구성 항목 | TBD — 확정 후 재평가 |
| FR-1.3 | 빌더 섹션이 포트폴리오보다 앞섬 | 부분 대응 — "만든 사람"을 먼저 보여주는 순서 설계 |
| FR-5.3 | 포트폴리오→문의 파라미터 연결 | 부분 대응 — 증거를 전환까지 이어주는 트래킹, 증거 자체는 아님 |

#### P-B. 실력이 어디서 왔는지 보여준다

| FR | 내용 요약 | 대응 정도 |
|---|---|---|
| FR-3.1 | "교육→실무투입→매니징" 인과 서술 | 대응 |
| FR-3.3 | 교육 과정 라인업(바이브코딩 중심) | 대응 |
| FR-3.4 | 누적 수치는 실제 값에만 사용 | 부분 대응 — 보조 신뢰 신호, 출처 서사의 핵심은 아님 |
| FR-3.2 | 에셋 소싱 정책(동화님 제공분 우선) | 부분 대응 — 표현 수단이지 원칙의 근거 자체는 아님 |

#### P-C. 맡기면 어떻게 관리되는지 보여준다

| FR | 내용 요약 | 대응 정도 |
|---|---|---|
| FR-4.1 | 8단계 프로세스 + 검수보고서·컨펌 실물 노출 | 대응 |
| FR-4.2 | 핵심 메시지(슬로건) | 대응 |
| FR-4.3 | 똑빌더 노출 형태 | TBD — 게스트 계정 사용 후 재평가 |
| FR-5.5 | 문의 접수 → 영업팀 전달 → 배정 | 부분 대응 — 관리 방식의 사후 증거, 사이트에 노출되는 콘텐츠는 아님 |

### 6-2. 매핑에서 제외한 FR

세 원칙 중 하나에 억지로 끼워 맞추기보다, 세 원칙을 담는 그릇이거나 운영 인프라인 FR은 매핑에서 제외했다.

| FR | 제외 이유 |
|---|---|
| FR-1.1, FR-1.2, FR-1.4, FR-1.5 | 랜딩 전체 구조·톤 규칙 — 특정 원칙이 아니라 3원칙을 담는 그릇 |
| FR-6.x (SEO/GEO) | 원칙을 "증명"하는 게 아니라 "노출"시키는 방식 |
| FR-7.x (CMS) | 3원칙의 콘텐츠를 입력하는 운영 도구, 원칙 자체와는 다른 층위 |

## 7. 기능 요구사항

상태: **확정**(회의록·Q&A로 결정) / **TBD**(착수 후 결정). 우선순위: P0/P1/P2.

### FR-1. 랜딩 (P0)

| ID | 요구사항 | 상태 |
|---|---|---|
| FR-1.1 | 8개 섹션 구성: 히어로 → 문제제기 → 선택기준 → 빌더 → 포트폴리오 → 교육·조직 → 일하는 방식 → 문의 | 확정 |
| FR-1.2 | 섹션마다 스크롤 인터랙션을 다르게 (§8 디자인 원칙) | 확정 |
| FR-1.3 | 빌더 섹션이 포트폴리오 섹션보다 앞선다 (사이트 정체 = 바이브코더의 장) | 확정 |
| FR-1.4 | 문제제기 섹션은 사고 사례 나열 없이 "구분이 안 된다" 수준으로 절제 | 확정 |
| FR-1.5 | 구성이 "선택 기준 제시형" — 판단 기준을 먼저 주고 그 기준으로 우리를 보게 함 | 확정 |

**인수 기준** — §8 'AI스러움' 실패 신호가 하나도 없을 것. 섹션마다 인터랙션이 다르고 각각 이유를 설명할 수 있을 것.

### FR-2. 포트폴리오 (P0) — 사람이 먼저

| ID | 요구사항 | 상태 |
|---|---|---|
| FR-2.1 | 빌더 목록 → 빌더 클릭 → 프로젝트 인라인 전개 뎁스 구조 | 확정 |
| FR-2.2 | 프로젝트 카드는 콘텐츠(문제→해결→결과)+실화면 이미지+**라이브 링크**를 동시 노출 | 확정 |
| FR-2.3 | 데이터 소스 2층: ①실전 사례 3건(에듀셀파·동행케어·카본벨트, 바이브코딩 건·다인원 제외) ②빌더 제작물 13명×1건+ | 확정 |
| FR-2.4 | 선정 워크플로: 팀 리스트업·1차 판정 → 대표 공유 → 대표 최종 확인 | 확정 |
| FR-2.5 | 빌더 기존 작업물은 'AI스럽지 않은' 페이지만 선별 (§8 체크리스트로 판정) | 확정 |
| FR-2.6 | 링크 등급(최상 실운영 / 상 배포 / 중 GitHub / 하 영상 / 최하 스크린샷) — "상"까지 소구 성립 | 확정 |
| FR-2.7 | 프로젝트 개별 URL(`/portfolio/:slug`) 부여 — 검색·AI 인용 진입점 | 확정 |

## 8. 디자인 요구사항

**절대 원칙** — 'AI스럽지 않을 것'. 실제 데이터 사용, 더미 목업 금지.

**판정 기준선 = 클라이언트 제공 레퍼런스 7건** (카카오뱅크 서비스·앤써, 우리은행 스팟, 미래엔 AIDT, 코들 AI, 이투스 청솔, 셀펍). 취향 참고가 아니라 합격선의 정의이며, **분석 전에는 랜딩 설계에 착수하지 않는다.**

### 'AI스러움' 체크리스트 (포트폴리오 선별 기준 겸용)

| ❌ 실패 신호 | ⭕ 합격 방향 |
|---|---|
| 모든 섹션이 동일한 아래→위 스크롤 | 섹션마다 인터랙션 언어가 다름 |
| 타이틀·설명·카드 전 영역 애니메이션 | 절제 — 안 넣는 곳을 의도적으로 남김 |
| 통계 카운터가 데이터와 미연결 | 실제 값에만 사용, 없으면 섹션 뺌 |
| 이모지를 기능 아이콘으로 | 아이콘 세트 통일 |
| 동일 카드 컴포넌트 반복 | 섹션마다 다른 레이아웃 |
| 목업·가짜 대시보드·로렘입숨 | 실제 데이터·실제 배포 화면 |
| 보라·인디고 그라디언트/글로우 | 브랜드 색 의도적 선정 |
| 정형 순서(Hero→기능→가격→FAQ) | 우리 서사 순서 |
| 귀여운 캐릭터·마스코트 | B2B 전문성 톤 |

**에셋 정책** — 포트폴리오 실화면·라이브 링크는 실물 유지. 교육·배경·보조 이미지는 무료 에셋 허용(기준은 출처가 아니라 완성도). 이미지 생성 필요 시 Codex/GPT(클로드 이미지 생성 금지).

**톤** — 레퍼런스 공통 친근체("~해요") 기본, 전문성은 문체가 아니라 내용으로 증명.

## 11. 제작 프로세스

매뉴얼 8단계·검수보고서 포맷을 따르되 이 프로젝트에 맞게 조정.

**8단계** — 수주·채널개설 → 킥오프·계정수급 → 기획 → 디자인 → 개발 → 배포·SEO → 이관 → 종료·하자보수. 각 단계 사이 **검수보고서+컨펌**이 관문.

**이 프로젝트 조정** — ①계정 소유 방향 반전(§10) ②여러 안 검토 후 디벨롭하는 산출 방식(검수보고서 "조율된 결정사항"에 대안·채택 이유 기재) ③정산·내부/외부방 분리는 해당 없음(내부 실습).

**협업 방식** (클라이언트 지정, 임의 변경 금지) — 주간 미팅 기준(데일리 싱크 없음) · 시안은 "선택지 나열"이 아니라 "과정을 설명하는 결정"으로 · Slack 기본, 급한 건 전화(실시간 응답 기대 어려움) · 회의록은 사람이 기록.
