## 1. 문제 정의

### 1-1. 출발점 — "고객의 고객"

8/4 미팅에서 대표님께서 이렇게 말씀하셨습니다. **우리 고객은 대표님이고, 대표님의 고객은 외주를 의뢰하려는 사람들이다. 그들이 수많은 개발사 중 우리를 선택할 이유를 함께 고민하는 것이 디자인보다 중요하다.**

그래서 이 기획안은 화면 이야기부터 시작하지 않고, **대표님이 풀려는 문제**와 **발주자가 겪는 문제**를 먼저 정의했습니다. 이 두 가지가 정리되어야 어떤 화면이 왜 필요한지가 설명됩니다.

### 1-2. 대표님이 풀려는 문제

미팅에서 확인한 내용을 정리하면 이렇게 이어집니다.

| | 질문 | 답 |
|---|---|---|
| 1 | 왜 지금 이 사이트가 필요한가 | 바이브코딩 외주 문의가 **직접 들어오는 채널이 없다.** 본사 채널은 규모·단가가 다르고, 개인 네트워크로 들어온 건은 조직에 쌓이지 않는다 |
| 2 | 왜 문의가 필요한가 | 빌더에게 **배정할 일감**이 있어야 한다 |
| 3 | 왜 일감이 급한가 | 빌더 스쿨이 내건 것은 "수익화가 가능한 직무 교육"이고, 지금 **1기가 진행 중**이다. 수료 시점에 배정할 일감이 없으면 그 약속이 증명되지 않는다 |
| 4 | 증명되지 않으면 | 1기 성과 사례가 없어 **2기 모집 근거가 사라지고**, 빌더가 이탈하면 공급도 함께 사라진다 |

> **이 사이트는 홍보물이 아니라 교육 사업에 일감을 공급하는 통로이고, 1기의 성과 사례를 만들 첫 사이클입니다.** 판단이 갈릴 때는 이 기준으로 결정했습니다.

여기서 나오는 과제 네 가지입니다.

| | 과제 | 이 기획안의 대응 |
|---|---|---|
| ① | 외주 문의가 들어오는 유입 경로가 없다 | 검색·AI 노출 (§9) |
| ② | 본사와도, 개인 프리랜서와도 다른 자리인데 시장에 그 자리가 인식되어 있지 않다 | 포지셔닝·규모 적합성 안내 (§2-3, §8-3) |
| ③ | 1기라 조직에 보여줄 실적이 쌓여 있지 않다 | 실물 중심 증명 (§6-1) |
| ④ | 3주 뒤에 사이트가 멈추면 ①~③이 무효가 된다 | 관리자 화면 + 운영 가이드 (§7, §11-3) |

### 1-3. 발주자가 겪는 문제

미팅에서 짚어주신 시장 상황입니다. 취업난으로 개발자들이 바이브코딩 랜딩 페이지만 만들어 영업하는 사례가 늘었고, **데이터 연동조차 되지 않는 껍데기 페이지가 포트폴리오로 쓰이고 있습니다.** 발주자는 진짜와 가짜를 가려낼 방법이 없습니다.

왜 가려낼 수 없는지 짚어보면 이렇게 됩니다.

| | 질문 | 답 |
|---|---|---|
| 1 | 왜 발주처를 고르기 어려운가 | 후보들이 다 비슷해 보이고, 실력을 확인할 방법이 없어서 |
| 2 | 왜 확인이 안 되는가 | 홈페이지에 있는 것이 결과물 이미지와 대표 소개뿐이라서 |
| 3 | 왜 그것뿐인가 | **"진짜 만들 수 있나" "실력이 어디서 왔나" "맡기면 어떻게 관리되나"** — 이 세 가지를 아무도 보여주지 않아서 |

**세 번째 줄의 질문 세 개가 이 사이트의 뼈대입니다.** 아무도 안 보여주고 있으므로, 보여주기만 해도 시장에 없는 것이 됩니다.

## 2. 해결 방향

### 2-1. 세 개의 축

| 축 | 답하는 질문 | 보여주는 방법 |
|---|---|---|
| **일하는 방식** | 맡기면 어떻게 관리되나 | 8단계 프로세스 · 검수보고서 · 컨펌 · 똑빌더 |
| 포트폴리오 | 진짜 만들 수 있나 | **열리는 라이브 링크** + 담당 빌더 이름 |
| 교육 | 실력이 어디서 왔나 | 수료 과정 · 커리큘럼 · 과정 라인업 |

**일하는 방식을 맨 위에 둔 이유** — 미팅에서 "우리가 어떻게 일하는가를 디테일하게 보여주는 것이 핵심 차별점"이라고 지목해 주셨습니다. 나머지 두 축은 그 주장을 뒷받침합니다.

**세 축은 서로를 보증합니다.** 포트폴리오만 있으면 위조 의심을 벗지 못하고, 교육만 있으면 교육 홍보로 읽히고, 일하는 방식만 있으면 말뿐인 프로세스가 됩니다. 세 축을 연결하는 것 자체가 요구사항입니다.

> 똑빌더라는 이름은 외부에 알려져 있지 않으므로 전면에 쓰지 않습니다. 전달할 메시지는 **"AI 시대에 최적화된 방식으로, AI와 함께 일합니다"**이고 똑빌더는 그 증거물입니다.

### 2-2. 과제 → 축 → 화면

| 과제 | 대응 | 해당 화면 |
|---|---|---|
| ① 유입 경로 없음 | 검색·AI 노출, 프로젝트별 독립 주소 | §9 · `/portfolio/<프로젝트>` |
| ② 자리가 인식되지 않음 | 선택 기준을 먼저 제시 + 규모 적합성 안내 | 랜딩 2·3·8번 섹션 |
| ③ 실적 공백 | 세 축 + 실물 중심 증명 | 랜딩 4~7번 섹션 |
| ④ 운영 공백 | 관리자 화면 + 운영 가이드 | §7 · §11-3 |

### 2-3. 브랜드 구조와 본사와의 관계

| 항목 | 내용 |
|---|---|
| 상위 브랜드 | AI 빌더 그룹 |
| 축 1 | 빌더 스쿨 — 교육 |
| 축 2 | 크루/커뮤니티 — 세미나·스터디 (구상 단계) |
| 현재 포지셔닝 | 바이브코딩 외주 전문 개발사 |
| 장기 방향 | AX 컨설팅 확장 |

교육 과정이 여러 개 준비되고 있다는 사실 자체가 소구점입니다. 단발성 강의가 아니라 직무별 과정을 갖춰 가는 조직이라는 뜻이고, 이것이 "이 조직은 계속 있을 것"이라는 근거가 됩니다.

**커뮤니티는 이번 범위에서 뺍니다.** 없어서가 아니라 1기가 진행 중이라 수료생·세미나 이력이 아직 없기 때문입니다. 지금 만들면 빈 페이지가 됩니다. 주소와 데이터 구조에 자리만 잡아두고 1기 수료 후에 채웁니다.

#### 본사와는 다른 시장입니다

| | 똑똑한개발자 본사 | AI 빌더 그룹 |
|---|---|---|
| 인력 | 경력 개발자·디자이너·기획자 | 바이브코더 |
| 규모 | 크고 다인원 | 작고 빠름 |
| 고객 | 예산·조직을 갖춘 곳 | 큰 개발사를 쓰기 어려운 곳 |
| 무기 | 축적된 경력·실적 | 속도와 규모 적합성 |

**가격을 무기로 내세우지 않습니다.** 싸다고 하면 개인 프리랜서와 같은 싸움이 되어 조직을 운영하는 쪽이 불리합니다. 소구점은 **"이 규모에는 이 방식이 맞다"**입니다.

#### 사이트에 본사를 어떻게 표기할지는 확인이 필요합니다

한 줄 포지셔닝은 **"검증된 바이브코더를, 조직이 보증해서 붙여준다"**입니다. 여기서 보증하는 조직이 AI 빌더 그룹인지 본사인지가 정해져야 신뢰의 출처가 성립합니다. 1기라 실적이 없는 상황(과제 ③)을 가장 빠르게 보완할 수 있는 수단이기도 합니다.

| 안 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| A | "똑똑한개발자가 만든" 수준으로 관계를 밝힘 | 본사 업력으로 실적 공백을 즉시 보완 | 본사 브랜드 희석. 본사 단가 기준의 문의가 들어올 수 있음 |
| B | 별도 브랜드로 독립, 회사 정보 수준만 표기 | 브랜드 혼선 없음 | 신뢰를 세 축만으로 전부 만들어야 함 |

> A안의 리스크(규모가 맞지 않는 문의)는 §8-3의 규모 적합성 안내로 상당 부분 해소됩니다. 회신 전까지는 A안을 전제로 설계하되, **표기를 넣고 빼기만 하면 되도록 해당 영역을 분리해서 만들겠습니다.** (§12 확인 4)

## 4. 정보구조

```
/                        랜딩
├─ /builders             빌더 목록
│  └─ /builders/<이름>    빌더 상세 — 프로젝트가 클릭 없이 펼쳐짐
├─ /portfolio/<프로젝트>  프로젝트 개별 주소 — 검색 진입점
├─ /courses              교육 과정
│  └─ /courses/<과정>     과정 상세 — 수료 빌더 목록
├─ /process              일하는 방식
├─ /contact              문의
└─ (/community)          커뮤니티 — 2차, 자리만 확보
```

**깊이는 2단을 넘지 않습니다.** 빌더 상세에서 프로젝트가 다 보이고, 프로젝트 개별 주소는 검색과 AI 답변에서 바로 들어올 수 있는 입구입니다.

**탭도 각자 주소를 갖습니다.** 교육 과정·포트폴리오 필터는 화면상 탭이지만 주소가 달라서 따로 색인되고 따로 집계됩니다. 포트폴리오는 서비스 특성별로 경로를 나눠(§6-3) **어떤 성격의 프로젝트가 문의로 이어지는지** 봅니다. 미팅에서 말씀하신 것처럼 본사도 'AI'에서 '개발사' 쪽으로 포지셔닝을 옮기셨는데, 그런 판단에 쓸 데이터를 처음부터 쌓아두려는 것입니다.

**빌더 페이지는 요약, 프로젝트 페이지는 전문**으로 분량을 다르게 씁니다. 목적이 달라 중복 문제가 생기지 않고, 프로젝트 페이지가 독립된 검색 입구로 작동합니다.

## 5. 화면 설계

### 5-1. 랜딩 — 고르는 기준을 먼저 드립니다

발주자의 문제가 "가려낼 수 없다"이므로, **"이렇게 고르세요"라는 기준을 먼저 제시하고 그 기준으로 우리를 보게 하는** 구성으로 갑니다. 비교표 형태라 AI 검색에 인용되기도 좋습니다.

| # | 섹션 | 답하는 질문 |
|---|---|---|
| 1 | 히어로 | 여긴 뭐 하는 곳인가 |
| 2 | 문제 제기 | 왜 고르기 어려운가 |
| 3 | 선택 기준 | 어떻게 골라야 하나 |
| 4 | 포트폴리오 | 무엇을 만들었나 |
| 5 | 빌더 | 누가 만들었나 |
| 6 | 교육·조직 | 실력이 어디서 왔나 |
| 7 | 일하는 방식 | 맡기면 관리되나 |
| 8 | 규모 적합성 | 우리 같은 프로젝트에 맞나 |
| 9 | 문의 | 얘기해 볼까 |

- **포트폴리오(4)를 빌더(5)보다 먼저 보여줍니다.** 발주자가 가장 먼저 확인하려는 것이 "무엇을 만들었나"이므로 결과물을 앞에 두고, 각 프로젝트에서 **"이걸 만든 사람"으로 빌더를 연결**합니다. 빌더 축이 빠지는 것은 아니고, 포트폴리오 카드마다 담당 빌더가 함께 붙습니다. 빌더 목록에서 프로젝트로 들어가는 경로(§4)는 그대로 유지되며, 랜딩에서의 노출 순서만 조정한 것입니다.
- **문제 제기(2)는 절제합니다.** 외주 사고 사례를 나열하지 않고 "선택지는 많은데 구분이 안 된다" 수준으로만 씁니다. 외주 자체에 대한 부정적 인상을 주면 손해입니다.
- **섹션마다 스크롤 인터랙션을 다르게 합니다.** 미팅에서 지적하신 AI스러움의 핵심이 "인터랙션이 너무 일관적"이라는 점이었습니다.

### 5-2. 하위 페이지

| 페이지 | 구성 |
|---|---|
| `/builders/<빌더>` | 프로필 → 프로젝트 펼침 → 문의 |
| `/portfolio/<프로젝트>` | 문제→해결→결과 + 실화면 + 라이브 링크 + 담당 빌더 → 문의 |
| `/courses/<과정>` | 커리큘럼 → 수료 빌더 → 각자의 프로젝트 |
| `/process` | 일하는 방식 + 8단계 프로세스 |

### 5-3. 빌더 페이지는 영업 자료이기도 합니다

문의가 들어오면 영업팀이 **적합한 빌더의 프로필 주소를 발주자에게 보내 반응을 확인**하게 됩니다. 그래서 이 페이지는 사이트 안에서 도달하는 화면이 아니라 **혼자 떨어져 나가도 설득이 되는 단위**여야 합니다.

- 사이트 맥락 없이 열어도 누구인지·무엇을 만들었는지·어디서 배웠는지가 그 페이지에서 끝날 것
- 카카오톡·슬랙에 붙였을 때 **빌더별로 다른 미리보기 카드**가 뜰 것 (공통 이미지가 뜨면 영업 자료로 못 씁니다)
- 그 페이지 안에서 바로 문의로 연결될 것

## 6. 포트폴리오

### 6-1. 실적이 없는 구간을 어떻게 다룰 것인가

1기가 진행 중이라 누적 수강생·프로젝트 건수·고객사 로고 같은 흔한 신뢰 지표가 아직 없습니다. 이 구간을 어떻게 다루느냐가 사이트 톤 전체를 좌우합니다.

> **없는 숫자를 만들지 않고, 열어서 확인되는 실물로 소구합니다.**

| 안 쓰는 것 | 대신 쓰는 것 |
|---|---|
| 값이 없는 통계 카운터 | 실제로 열리는 라이브 링크 |
| 고객사 로고 나열 | 프로젝트별 서술 + 담당 빌더 이름 |
| 추상적인 역량 문구 | 8단계 프로세스와 검수·컨펌 실물 |

이 방향은 주신 레퍼런스와도 맞습니다. 미래엔 AIDT는 수치를 앞세우지 않고 체험 링크와 데모로 신뢰를 만드는데, 저희의 라이브 링크가 같은 역할을 합니다.

> 소구를 약하게 하자는 뜻은 아닙니다. **검증 가능성을 소구점으로 내건 사이트가 검증되지 않는 숫자를 쓰면 주장 자체가 무너지므로**, 소구력을 실물 쪽에서 만들자는 것입니다.

### 6-2. 콘텐츠와 링크를 둘 다 넣습니다

| 요소 | 역할 |
|---|---|
| 콘텐츠 + 이미지 | 검색에 걸리는 실체. 없으면 프로젝트 단위 검색에 안 잡힘 |
| 바로가기 링크 | 검증 수단. 없으면 껍데기 포트폴리오와 구분 안 됨 |

미팅에서 "에어로케이 개발사"로 검색했을 때 똑개가 떠야 한다고 하신 것이 앞쪽이고, 실제 결과물로 바로 이동하는 것이 뒤쪽입니다. 목적이 달라 하나로 대체할 수 없습니다.

**모든 프로젝트는 우리 도메인 안에 상세 페이지를 하나씩 갖습니다.** 목록 카드에서 외부 결과물로 바로 나가는 버튼은 그대로 두되, 상세 페이지로 들어오는 링크를 반드시 함께 둡니다. 외부로만 내보내는 카드를 만들면 검색에 잡힐 콘텐츠가 우리 쪽에 남지 않기 때문입니다.

**상세 본문은 네 문항으로 통일합니다** — 무엇을 · 왜 · 어떻게 · 결과. 실전 사례든 빌더 제작물이든 같은 형식을 쓰며, 여기서 형식이 갈리면 §6-3에서 없앤 구분이 다시 드러납니다.

### 6-3. 자료는 두 곳에서 모으되, 화면에서는 나누지 않습니다

자료 수급은 두 갈래입니다.

| 출처 | 내용 | 규모 |
|---|---|---|
| 실전 사례 | 에듀셀파·동행케어·카본벨트 | 3건 |
| 빌더 제작물 | 빌더 개인 작업물 | 12명 × 1건 이상 |

다만 **화면에서는 이 둘을 구분해서 보여주지 않습니다.** 8/9에 대표님께서 짚어주신 대로, 목록이 "실전 사례 / 빌더 제작물"로 갈리면 한쪽이 연습작처럼 읽히고 **모든 빌더가 실전 경험을 가진 조직이라는 메시지가 무너집니다.**

대신 이렇게 나눕니다.

| 분류 축 | 내용 |
|---|---|
| **주 분류 (제안)** | **서비스 특성** — 랜딩·브랜드 사이트 / 웹 서비스 / 앱 / 내부 업무 도구 |
| 보조 태그 | 도메인·산업 — 교육, 커머스, 헬스케어 등 |

이 분류는 화면 필터인 동시에 **주소 경로**가 되어(`/portfolio/<분류>`), 어떤 성격의 프로젝트가 문의로 이어지는지 집계됩니다(§4). 되돌리기 쉬운 항목이라 위 축을 기본으로 진행하고, 다른 축이 좋으시면 언제든 바꾸겠습니다.

분류값은 **관리자 화면에서 프로젝트마다 지정**하고, 화면에서는 **목록 카드에 최대 2개, 상세 페이지에 전부** 표시합니다.

**목록 순서는 직접 조정할 수 있게 만듭니다.** 보여주고 싶은 프로젝트를 앞으로 올리는 방식이라, 분류를 나누지 않아도 강조하고 싶은 건이 먼저 보입니다.

**최소 기준** — 실제로 열리는 링크가 **8건 이상**이어야 "진짜 만들 수 있나"에 대한 답이 성립한다고 봅니다. 1주차에 판정하고, 미달이면 그리드 대신 소수 정예 서술형으로 바꾸고 일하는 방식 쪽 비중을 늘리겠습니다. 4건 이하로 떨어지면 그때 방향을 다시 상의드리겠습니다. 분류별로는 최소 2건이 모여야 나누고, 그보다 적으면 해당 분류는 합칩니다.

### 6-4. 선별 — 포트폴리오가 AI스러우면 안 됩니다

"AI를 잘 쓰는 곳은 다르다"가 우리 주장이므로, 포트폴리오가 AI 티를 내면 주장이 무너집니다. 수준이 낮은 라이브 링크는 스크린샷보다 해롭습니다.

| 판정 | 처리 |
|---|---|
| 통과 | 링크 그대로 노출 |
| 보완 가능 | 문제 항목만 수정 후 포함 |
| 미달 | 링크 없이 콘텐츠만, 또는 제외 |

**절차** — 팀 리스트업·1차 판정 → 대표님 공유 → 최종 확인 → 콘텐츠 제작. 판정 기준은 §10-2 체크리스트입니다.

### 6-5. 링크 등급

| 등급 | 형태 | 검증력 |
|---|---|---|
| 최상 | 실운영 서비스 | 완전한 증명 |
| 상 | 배포 결과물 | 실제 동작 확인 |
| 중 | GitHub | 비개발자에겐 약함 |
| 하 | 동작 영상 | 정지 이미지보다 나음 |
| 최하 | 스크린샷 | 위조 가능 |

**"상" 등급까지는 소구가 성립합니다.** 실전 사례의 링크 공개가 제한되면 "하"(영상)로 대체합니다.

### 6-6. 빌더 표기

표기명(실명/닉네임)과 이미지(실사/아바타/없음)는 개인이 고릅니다. 이력·수료 과정·기수는 공통으로 노출합니다. 이미지가 없어도 카드가 깨지지 않게 이니셜 대체 표시를 준비하고, 미리보기 카드는 이미지가 없는 빌더도 텍스트 기반으로 자동 생성합니다(§5-3).

표기 방식이 조금씩 다른 것은 오히려 "균일한 그리드 = AI 티"를 자연스럽게 완화합니다.

**프로젝트마다 대표 제작자 1명을 지정합니다.** 여러 명이 참여한 건이라도 "이 프로젝트를 만든 사람"이 한 명 특정되어야 발주자가 신뢰를 느끼고, 문의가 들어왔을 때 어느 빌더를 보고 왔는지도 명확해집니다(§8-2).

역할은 이렇게 나뉩니다.

| | 하는 일 |
|---|---|
| 대표 제작자 | 프로젝트 상세 본문을 작성 |
| 참여 빌더 | **아무것도 다시 쓰지 않음.** 본인 프로필만 관리하면 참여한 모든 프로젝트에 자동 반영 |
| 관리자 | 누가 대표이고 누가 참여인지 **지정** |

여러 명이 같은 본문을 동시에 고치면 덮어쓰기가 나기 때문에 편집 권한을 한 명에게 둡니다. 빌더가 스스로 대표를 바꿀 수는 없고, 관리자 화면에서 지정합니다.

### 6-7. 일하는 방식 — 8단계

```
수주·채널개설 → 킥오프·계정수급 → 기획 → 디자인 → 개발 → 배포·SEO → 이관 → 종료·하자보수
```

각 단계 사이에 검수보고서와 컨펌이 있습니다. `/process`에서 이 8단계를 설명하고, 똑빌더는 게스트 계정으로 직접 써본 뒤 노출 형태를 정합니다. 현재 게스트 계정에는 실데이터가 거의 없어, **실화면 캡처보다 업무 흐름 다이어그램 쪽이 유력**합니다. 실제 프로젝트 화면을 쓸 수 있게 되면 그쪽이 더 좋습니다.

## 7. 관리자 화면

### 7-1. 관리 대상

| 대상 | 항목 |
|---|---|
| 빌더 | 표기명·이미지·이력·수료 과정·기수 |
| 프로젝트 | 제목·설명·이미지·라이브 링크·담당 빌더 |
| 교육 과정 | 과정명·커리큘럼·기수·수료 빌더 |

등록할 때 검색용 정보(주소·제목·설명·미리보기 이미지)를 함께 입력합니다. 미팅에서 강조하신 대로 **첫 이미지가 미리보기 썸네일로 잡히도록** 처리하고, 외부 체커로 실측해서 확인합니다.

### 7-2. 권한 — 관리자 + 빌더 2단계

| 역할 | 누가 | 할 수 있는 것 |
|---|---|---|
| 관리자 | 대표님·영업팀장·응대 실무자 등 **복수 계정** | 전체 콘텐츠 등록·수정, 노출 여부와 순서 조정, 빌더 계정 관리 |
| 빌더 | 빌더 본인 | **본인 프로필과 본인이 담당한 프로젝트**만 등록·수정 |

빌더가 직접 자기 포트폴리오를 관리하면 관리자 한 명에게 등록 부담이 몰리지 않고, 2기 이후에도 콘텐츠가 계속 쌓입니다(과제 ④). 다만 **공개 버튼은 관리자만** 누를 수 있습니다. 빌더가 올린 것이 검토 없이 바로 공개되면 §6-4의 선별 기준이 무너지기 때문입니다.

**결재 라인은 만들지 않습니다.** 빌더 작성 → 팀장 승인 → 관리자 승인 같은 단계를 두면, 콘텐츠가 계속 늘어나는 구조에서 병목이 되고 여러 명이 훑고 지나가면 아무도 책임지지 않게 됩니다. 대신 **공개 권한을 한 사람에게 두고, 누르기 전에 확인할 항목을 체크리스트로 띄웁니다.**

| 공개 전 확인 (9항목) |
|---|
| 라이브 링크가 실제로 열리는가 · 노출 수치가 실제 값인가 · 모든 이미지에 대체 텍스트가 있는가 · 제목 40자 이내 · 설명 80~110자 · 미리보기 이미지가 지정됐는가 · 본문 4문항이 채워졌는가 · 담당 빌더가 연결됐는가 · 공개 금지 대상이 없는가 |

미충족이어도 막지 않고 경고만 띄웁니다. 최종 판단은 사람이 합니다.

### 7-3. 블로그 · 인사이트 · FAQ는 이번 범위에서 제외합니다

미팅에서 인사이트·FAQ 이야기가 나왔는데, 이는 **똑개 사이트의 콘텐츠를 예로 들어 "SEO를 어느 수준까지 준비해야 하는가"를 설명하신 맥락**이었던 것으로 정리했습니다. 이번 랜딩 페이지에는 해당하지 않아 제외합니다.

다만 개발 환경(orca)에 글 발행 구조가 이미 들어 있어, **그 구조를 제거하지 않고 비활성 상태로 남겨둡니다.** 나중에 콘텐츠가 필요해지면 처음부터 만들 필요 없이 열 수 있습니다.

### 7-4. 관리자 화면은 3주 뒤를 위한 것입니다

2기 수료생과 새 프로젝트가 계속 올라와야 콘텐츠가 늘고, 콘텐츠가 늘어야 검색 노출도 늡니다(과제 ④). 그래서 등록 화면은 **개발자가 아닌 담당자가 혼자 쓸 수 있는 수준**까지를 기준으로 잡았습니다. 인계 문서는 §11-3에 정리했습니다.

## 8. 문의 · 리드

### 8-1. 폼은 그대로, 간단하게

플러그 폼을 그대로 연동해 문의가 CRM에 바로 쌓이게 합니다. **항목은 늘리지 않습니다.** 예산·일정·회사 규모를 물으면 이탈이 생긴다고 하신 판단에 동의합니다.

### 8-2. 어느 빌더를 보고 문의했는지 남깁니다

"발주자가 빌더를 고르는 구조"를 실제로 작동시키는 연결입니다. 문의 버튼에 파라미터(`?ref=<프로젝트>&builder=<대표 제작자>`)를 실어, 어느 프로젝트·빌더를 보고 왔는지를 문의 기록에 남깁니다. **화면에 보이는 입력 항목은 늘지 않습니다.**

문의 버튼은 공통 부품 하나를 세 곳에 놓되, **놓인 자리에 따라 문구와 파라미터가 달라집니다.**

| 어디서 눌렀나 | 버튼 문구 | 붙는 값 |
|---|---|---|
| 랜딩 | 프로젝트 상담하기 | 홈 유입 |
| 프로젝트 상세 | 이 프로젝트와 비슷한 의뢰하기 | 프로젝트 |
| 빌더 상세 | 이 빌더의 경험으로 상담받기 | 빌더 |

같은 "문의하기"를 세 곳에 붙이면 맥락이 사라집니다. 프로젝트를 보다 누르는 사람과 빌더 이력을 보다 누르는 사람은 하려는 말이 다릅니다.

플러그 폼에 파라미터를 넣을 수 있다고 확인해 주셔서, **가이드 문서를 받는 대로 연동하겠습니다.** 프로젝트마다 대표 제작자를 1명 지정하는 것(§6-6)이 이 연결을 깔끔하게 만듭니다.

### 8-3. 규모 적합성 안내 — 항목을 늘리지 않고 문의 질을 올립니다

목표는 문의 건수가 아니라 **빌더에게 배정할 수 있는 문의**입니다. 그런데 폼으로 예산을 물을 수는 없습니다. 그래서 문의 직전에 발주자가 스스로 판단하도록 합니다.

| 항목 | 내용 |
|---|---|
| 위치 | 랜딩 8번 섹션 + `/contact` 상단 |
| 형식 | 가격은 쓰지 않고, **"이런 프로젝트에 맞습니다 / 이런 건 이렇게 연결합니다"** 대비 |
| 맞는 예 | MVP·랜딩·내부 도구·기존 서비스 개선 등 작고 빠른 단위 |
| 연결하는 예 | 대규모·다인원·장기 운영 건 → 본사로 연결 |

이 한 섹션이 동시에 해결하는 것: ①맞지 않는 문의가 줄어 영업 부하가 낮아지고 ②"싸서"가 아니라 "이 규모에 맞아서"라는 소구가 화면에 실체로 생기고 ③본사가 경쟁이 아니라 상위 연결처가 되어 §2-3 A안의 부담이 줄고 ④적합/부적합 대비가 비교표라 AI 검색에 인용되기 좋습니다.

> 본사로 연결하는 방식(링크 이동 / 문의 후 내부 전달 / 문구만 표기)은 §12 확인 4와 함께 정해 주시면 반영하겠습니다.

## 9. 검색 노출 (SEO / GEO)

> 과제 ①에 직접 대응하는 영역이라 **이번 프로젝트에서 가장 우선순위가 높습니다.** 미팅에서 말씀하신 대로 콘텐츠가 아무리 좋아도 기술 세팅이 안 되면 노출되지 않습니다.

### 9-1. 키워드 — 방향 확정

8월 7일에 대표님께 문의드려 조정 방향에 동의해 주셨습니다. 확인된 내용은 이렇습니다.

| 확인 사항 | 내용 |
|---|---|
| 타깃이 그 말을 쓰는가 | 내부 개발팀이 없는 중소기업 대표가 "바이브코딩"이라는 용어를 알고 검색창에 입력할지 불확실 |
| 전례 | 똑개에서도 **"AX 전환을 위한 전문 개발사"라는 전문용어 포지셔닝으로 리드 수집에 실패**해 "개발사"라는 일반 용어로 되돌린 경험 |
| 실제 데이터 | **현재 똑개 유입 키워드 1위는 "AI"**. 바이브코딩이 아님 |
| 대표님 의견 | 앱 개발·웹 개발·서비스 개발 쪽이 더 먹힐 것. **"AI 웹/앱 개발사"**도 좋겠다 |

**여기서 나오는 원칙은 "전문용어로 포지셔닝하지 않는다"입니다.** 실패한 것은 AI가 아니라 업계 용어였습니다. AI는 오히려 가장 강한 유입 키워드이므로 그대로 살리고, 발주자가 실제로 쓰는 일반 용어와 붙입니다.

| 영역 | 키워드 |
|---|---|
| 리드를 받는 페이지 (홈·포트폴리오·문의) | **AI 웹 개발 · AI 앱 개발 · AI 웹/앱 개발사 · 서비스 개발** |
| 교육 페이지·섹션 | 바이브코딩 · 바이브코딩 교육 |
| 화면 문구·브랜드 표현 | 기존 포지셔닝 그대로 유지 |

**검색으로 들어오는 통로만 바꾸는 것이고 포지셔닝은 그대로입니다.**

세부 키워드는 팀 리서치를 거쳐 별도 제안드리기로 했습니다.

### 9-2. AI 검색 대응

AI 검색에서 브랜드가 언급되는 경로는 자사 사이트만이 아니라 비교글·리스트 글 같은 제3자 페이지인 경우가 많습니다. 사이트 안에서는 포트폴리오·빌더·교육·규모 적합성을 **2~3줄로 끊어지는 자기완결 문단과 비교표**로 구성해 인용되기 쉽게 만들고, 외부 채널 노출은 발행 이후 운영 과제로 함께 제안드립니다.

### 9-3. 기술 세팅

- 서치콘솔·서치어드바이저·GA4·GTM 생성 → `jangwon@toktokhan.dev` 초대
- sitemap.xml · robots.txt(차단 해제 확인) · rss.xml · llms.txt
- 구조화 데이터: Organization + Article + FAQPage
- 페이지별 제목·설명·미리보기 이미지 개별 지정 (**빌더·프로젝트는 필수**)
- 색인 확인 (`site:도메인`)

제목은 40자 이내, 핵심어는 앞 15자 안에. 설명은 80~110자.
예) `바이브코딩 외주 전문 개발사 | AI 빌더 그룹`

> **도메인 관련** — 검색 도구 등록과 색인 확인은 도메인이 있어야 진행됩니다. 도메인 전달을 기다리며 일정이 밀리지 않도록, **임시 주소에서 세팅과 검증을 먼저 끝내 두고 실제 도메인이 정해지면 그대로 옮기겠습니다.**

### 9-4. 유입 측정

외부에서 들어오는 경로(UTM)와 사이트 내부 경로(탭·카테고리 주소)를 나눠서 봅니다. GA4 이벤트는 최소 3종 — 문의 폼 진입, 제출, 포트폴리오 링크 클릭.

| 같은 카드 컴포넌트 반복 | 섹션마다 다른 레이아웃 |

| | 개발 | 콘텐츠 | 마무리 |
|---|---|---|---|

| 2주차 | 랜딩·포트폴리오·빌더·교육·프로세스·관리자 | 프로젝트 상세·실화면 정리 | 개발 검수 → 컨펌 |
| 3주차 | 플러그 연동·검색 세팅·QA | 워딩 최종 · **운영 가이드 작성** | 배포 → 이관 → 종료 |

콘텐츠를 따로 관리하는 이유는 **자료 수급과 선별이 일정을 좌우하는 가장 큰 변수**이기 때문입니다. 1주차에 끝내서 물량을 조기에 파악합니다.

**착수 즉시** — 똑빌더 게스트 사용 · 플러그 가입 후 파라미터 확인 · 빌더 작업물 12건 선별 · 개발사 포트폴리오 사이트 조사 · 교육 에셋 요청 · 검색 도구 계정 생성.

**인계 산출물** — 관리자 사용 가이드(등록 절차·검색 정보 입력 기준·이미지 규격) · 콘텐츠 추가 기준 · 계정 인계표 · 운영 담당자와 주기.

**2차로 넘기는 것** — 커뮤니티/세미나 페이지 · 누적 수치 노출 · 블로그 공개 · 고도화 인터랙션. 1차에서는 주소와 데이터 구조에 자리만 잡아둡니다.

### 11-4. 성과 확인

**인수 시점 (이번 프로젝트가 책임지는 범위)** — 검색 도구 6종 세팅 완료 · 색인 진입 확인 · GA4 이벤트 정상 수집 · 세 축 모두 실데이터 · 인계 산출물 전달.

**발행 이후 (운영 성과)** — 2주 뒤 색인 페이지 수 → 1개월 뒤 키워드 순위·경로별 세션 → 2~3개월 뒤 문의 건수·포트폴리오 경유 비율.

목표 수치는 킥오프에서 함께 정해 주시면 그 기준으로 보고드리겠습니다.
