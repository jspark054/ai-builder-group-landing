## 1. 무엇을, 왜 만드는가

**무엇** — 랜딩 1종 + 하위 페이지(빌더·포트폴리오·교육·일하는 방식·문의) + 관리자 화면.

### 1-1. 대표님이 풀려는 문제

| | 질문 | 답 |
|---|---|---|
| 1 | 왜 이 사이트가 필요한가 | 바이브코딩 외주 문의가 직접 들어오는 채널이 없다 |
| 2 | 왜 문의가 필요한가 | 빌더에게 배정할 일감이 있어야 한다 |
| 3 | 왜 급한가 | 빌더 스쿨의 약속이 "수익화 가능한 직무 교육"인데 1기가 진행 중이다. 수료 시점에 일감이 없으면 약속이 증명되지 않는다 |
| 4 | 증명 실패 시 | 2기 모집 근거가 사라지고 빌더 이탈로 공급도 사라진다 |

**이 사이트는 홍보물이 아니라 교육 사업의 일감 공급 통로다.** 판단이 갈릴 때의 기준.

| 과제 | 대응 |
|---|---|
| ① 유입 경로 없음 | FR-6 (검색 노출) → **P0** |
| ② 자리가 인식되지 않음 | FR-1.5 · FR-1.6 · FR-1.7 |
| ③ 실적 공백 | FR-2 · FR-4 + 원칙 P-D |
| ④ 운영 지속성 | FR-7 → **P1**, FR-7.5 |

### 1-2. 발주자가 겪는 문제

껍데기 랜딩 페이지가 포트폴리오로 쓰이는 상황에서 발주자는 진짜와 가짜를 구분하지 못한다. "진짜 만들 수 있나 / 실력이 어디서 왔나 / 맡기면 어떻게 관리되나" 세 질문에 아무도 답하지 않기 때문이다. 이 세 질문이 세 축이 된다.

**한 줄 포지셔닝** — 검증된 바이브코더를, 조직이 보증해서 붙여준다.
보증하는 조직이 AI 빌더 그룹인지 본사인지는 미확정 (FR-1.7).

## 2. 성공 기준

**비즈니스 목표** — 문의 수집 → 영업팀 전달 → 빌더 배정. 최종 목표는 문의 건수가 아니라 배정이다.

### 2-1. 인수 시점 (우리가 책임지는 범위)

| 항목 | 판정 기준 |
|---|---|
| 검색 도구 6종 | sitemap·robots·GA4·서치콘솔·서치어드바이저·GTM 완료 |
| 색인 진입 | 임시 도메인에서 `site:` 색인 확인 완료. 실제 도메인 연결은 이관 시 |
| 계측 동작 | GA4 이벤트 3종 정상 수집 |
| 문의 경로 전달 | 파라미터 전달 성공 또는 GA4 매칭 대체 동작 확인 |
| 실데이터 충족 | 세 축 전부 실데이터, 더미 0건 |
| 인계 완료 | FR-7.5 산출물 전달 |

### 2-2. 발행 이후 (운영 성과)

D+2주 색인 페이지 수 → D+1개월 키워드 순위·경로별 세션 → D+2~3개월 문의 건수·포트폴리오 경유 비율. 분류별(FR-2.10) 유입 비율은 지표가 아니라 **포지셔닝 판단 입력값**.

### 2-3. 대표님 목표 기준 (사이트 단독 계측 불가)

```
문의 수 → 배정 가능한 문의 → 실제 배정 건수 → 빌더별 배정 편차
 (사이트)      (영업팀 판정)        (대표님 측 데이터)
```

사이트가 기여할 수 있는 지점은 **"배정 가능한 문의"의 비율**이고, FR-1.6이 그 장치다. 목표 수치는 킥오프 합의 대상.

## 3. 사용자

| 구분 | 누구 | 필요한 것 |
|---|---|---|
| 1차 | **발주자** — 웹/앱 외주를 맡기려는 스타트업 대표·사업 담당자. 예산 수백만~수천만 원. 똑개와 경쟁사를 구분하지 못함 | 맡겨도 되는지 판단할 근거. 로고·수치가 아니라 일하는 방식과 실물 |
| 2차 | **영업팀** — 문의가 오면 적합한 빌더 프로필을 발주자에게 보내 반응 확인 | 단독으로 공유되는 빌더 페이지 (FR-2.9) |
| 3차 | **콘텐츠 관리자** — 빌더·프로젝트·교육 등록 | 개발자 없이 쓸 수 있는 관리자 화면. 3주 이후 담당자 미지정 (FR-7.5) |
| 발주 주체 | **대표님** — 최종 컨펌 주체 | — |

**발주자 여정** — 검색 유입 → 포트폴리오로 실력 확인 → 교육 이력으로 신뢰 보강 → 일하는 방식으로 리스크 안심 → 규모 적합성 확인 → 문의.

## 4. 범위

### 포함

랜딩 + 하위 페이지 / 규모 적합성 섹션 / **관리자 + 빌더 2단계 권한** / 플러그 폼 연동(파라미터 포함) / 검색 세팅 6종 + 페이지별 미리보기 개별 지정 / 실데이터 반영 / Vercel 배포 후 이관 / 운영 가이드.

### 제외

| 항목 | 사유 |
|---|---|
| 블로그·인사이트·FAQ | 미팅에서 언급된 인사이트·FAQ는 **똑개 사이트의 콘텐츠를 예로 든 것**(SEO 준비 수준 설명 맥락)이며 이 랜딩에는 해당 없음. 제외 확정. 보일러플레이트 발행 구조는 비활성으로 남김(FR-7.6) |
| 크루/커뮤니티 | 1기 진행 중이라 실적 없음. 자리만 확보 |
| 사이트 내 결제·견적 계산기 | 고가 외주라 전화 영업으로 전환 |
| 가격·견적 범위 표기 | 저가 경쟁 회피. 가격 대신 규모 적합성으로 소구 (FR-1.6) |
| 발주자 회원가입 | 이탈 요인 |
| 문의 데이터 자체 저장 | 플러그 CRM 담당 |
| AX 컨설팅 전용 콘텐츠 | 장기 |
| 다국어 | 언급 없음 |

## 5. 정보구조

```
/                     홈 — 9개 섹션
/builders             빌더 목록
/builders/:name       빌더 상세 (영업 공유 단위)
/portfolio/:slug      프로젝트 개별 주소 (검색 진입점)
/portfolio/:category  서비스 특성별 분류 (랜딩·웹서비스·앱·내부도구)
/courses              교육 과정
/courses/:name        과정 상세
/process              일하는 방식
/contact              문의
(/community)          2차, 자리만 확보
```

**깊이** — 빌더 상세에서 프로젝트가 클릭 없이 전부 보임(1뎁스). 프로젝트 개별 주소는 검색·AI 인용 진입점.
**중복 처리** — 빌더 페이지는 요약, 프로젝트 페이지는 전문. 분량이 달라 중복이 생기지 않으므로 canonical 미적용.
**규모** — 구현 대상 페이지 약 19개(동적 생성 포함). 2주차 개발 물량 산정 기준.
**포트폴리오 분류** — 실전/제작물 구분 없이 단일 목록. 경로 분류는 서비스 특성 기준(FR-2.10).

## 6. 제품 원칙

| 원칙 | 문장 | 축 |
|---|---|---|
| **P-C** | **맡기면 어떻게 관리되는지 보여준다** | **일하는 방식 — 대표님이 지목한 핵심 차별점** |
| P-A | 진짜 만들 수 있다는 걸 보여준다 | 포트폴리오 |
| P-B | 실력이 어디서 왔는지 보여준다 | 교육 |
| P-D | 없는 숫자를 만들지 않고, 열어서 확인되는 실물로 소구한다 | 전 축 공통 (표현 제약) |

**P-D는 네 번째 축이 아니라 표현 제약이다.** P-A~C가 "무엇을 보여줄까"라면 P-D는 "어떻게 보여주면 안 되는가"다. 1기라 누적 수치·고객사 로고·수상 이력이 없는데, 이 공백을 관행적으로 메우는 순간 검증 가능성을 내건 사이트의 주장이 무너진다.

| 안 씀 | 대신 |
|---|---|
| 값 없는 카운터 | 라이브 링크 (FR-2.2·2.6) |
| 고객사 로고 나열 | 프로젝트별 서술 + 담당 빌더 (FR-2.2·2.7) |
| 추상적 역량 문구 | 8단계 프로세스 실물 (FR-4.1) |

> 소구를 약하게 하자는 뜻이 아니다. 대표님께서 "결국 셀링"이라고 하신 만큼 소구력은 필요하고, **그 소구력을 실물 쪽에서 만들자**는 것이다.

### 6-1. 원칙 → FR 매핑

**대응** = 화면 콘텐츠로 직접 드러남 / **부분** = 뒷받침하지만 간접적.

| 원칙 | 대응 | 부분 |
|---|---|---|
| P-C | FR-4.1 (프로세스·검수 실물) · FR-4.2 (슬로건) | FR-1.6 (맡길 범위 명시) · FR-5.5 (배정 프로세스) · FR-4.3 (TBD) |
| P-A | FR-2.2 (콘텐츠+실화면+링크) · FR-2.3 (단일 목록) · FR-2.6 (링크 등급) · FR-2.7 (개별 주소) · FR-2.11 (대표 제작자 특정) | FR-2.1 (경로) · FR-2.4 (선정 절차) · FR-2.5 (선별) · FR-2.9 (전달) · FR-1.3 (결과물 우선 순서) · FR-2.10·2.12 (분류·순서) · FR-5.3 (트래킹) |
| P-B | FR-3.1 (인과 서술) · FR-3.3 (라인업) | FR-3.4 (수치 절제) · FR-3.2 (에셋) |
| P-D | FR-3.4 · FR-2.6 · §8 체크리스트 | FR-2.5 · FR-1.8 (TBD) |

**매핑 제외** — FR-1.1·1.2·1.4·1.5(원칙을 담는 그릇) · FR-1.7(확정 시 전제가 바뀜) · FR-6(증명이 아니라 노출) · FR-7(운영 도구).

## 7. 기능 요구사항

### FR-1. 랜딩 (P0)

| ID | 요구사항 | 상태 |
|---|---|---|
| FR-1.1 | 9개 섹션: 히어로 → 문제제기 → 선택기준 → **포트폴리오 → 빌더** → 교육·조직 → 일하는 방식 → 규모 적합성 → 문의 | 확정 (8/9 순서 변경) |
| FR-1.2 | 섹션마다 스크롤 인터랙션을 다르게 (AI스러움의 핵심 지적 사항) | 확정 |
| FR-1.3 | **포트폴리오 섹션이 빌더보다 앞선다.** 1기라 빌더 개인 경력이 얇아 사람을 먼저 세우면 신뢰가 약해진다. 결과물 → "이걸 만든 사람" 순서. 포트폴리오 카드마다 담당 빌더 동반 표기 | 확정 (8/9 변경) |
| FR-1.4 | 문제제기 섹션은 사고 사례 나열 없이 "구분이 안 된다" 수준으로 절제 | 확정 |
| FR-1.5 | 선택 기준 제시형 구성 — 판단 기준을 먼저 주고 그 기준으로 보게 함 | 확정 |
| FR-1.6 | 규모 적합성 안내. 가격 미표기, "이런 프로젝트에 맞습니다 / 이런 건 이렇게 연결합니다" 대비. 문의 직전 + `/contact` 상단 | 확정 (연결 방식은 FR-1.7 연동) |
| FR-1.7 | 본사와의 관계 표기 수위. 잠정 A안(관계 명시), 넣고 빼기 쉽게 분리 구현 | **TBD — 대표님 판단** |
| FR-1.8 | "1기 진행 중" 현황의 노출 수위 | **TBD — 대표님 판단** |

**인수 기준** — §8 실패 신호 0건. 섹션별 인터랙션이 다르고 각각 이유를 설명할 수 있을 것. **FR-1.7·1.8 영역을 제거해도 레이아웃이 깨지지 않을 것.**

> **FR-1.6의 의도** — 폼 항목을 늘리지 않고(FR-5.2) 문의 질을 올리는 유일한 장치. 동시에 ①저가가 아닌 적합성 소구를 화면 실체로 만들고 ②본사를 경쟁이 아닌 상위 연결처로 배치해 FR-1.7 A안의 부담을 낮추고 ③비교표 형식이라 AI 인용에 유리(FR-6.8).

### FR-2. 포트폴리오 (P0)

| ID | 요구사항 | 상태 |
|---|---|---|
| FR-2.1 | 빌더 목록 → 클릭 → 프로젝트 인라인 전개 | 확정 |
| FR-2.2 | 프로젝트 카드는 콘텐츠 + 실화면 + **라이브 링크** 동시 노출. **상세 본문은 4문항 통일 — 무엇을 · 왜 · 어떻게 · 결과** (출처에 따라 소제목이 갈리면 FR-2.3에서 없앤 구분이 다시 드러남) | 확정 |
| FR-2.3 | 수급은 2층(실전 3건 + 빌더 제작물 12명×1건+). **화면에서는 분리하지 않고 단일 목록.** "실전 / 제작물" 라벨 금지 — 한쪽이 연습작으로 읽히면 "모두 실전 경험이 있는 빌더" 메시지가 무너짐 | 확정 (8/9 대표님 회신) |
| FR-2.4 | 선정: 팀 리스트업·1차 판정 → 대표님 공유 → 최종 확인 | 확정 |

> **FR-6.1 근거 (8/7 대표님 회신)** — ①타깃 페르소나(내부 개발팀 없는 중소기업 대표)가 "바이브코딩"이라는 용어를 알고 검색할지 불확실하다 ②똑개도 **"AX 전환을 위한 전문 개발사"라는 전문용어 포지셔닝으로 리드 수집에 실패**해 "개발사"라는 일반 용어로 되돌린 전례가 있다 ③**현재 똑개 유입 키워드 1위는 "AI"**이며 바이브코딩이 아니다 ④대표님 제안 키워드는 앱 개발·웹 개발·서비스 개발, 그리고 "AI 웹/앱 개발사".
>
> **이전 문서의 "AX·AI 전면 배치 금지(검증된 실패)"는 잘못된 정리였다.** 실패한 것은 AI가 아니라 **"AX 전환"이라는 업계 용어**다. AI는 오히려 가장 강한 유입 키워드이므로 살리고, 발주자가 실제로 쓰는 일반 용어와 결합한다.
>
> 원칙: **전문용어로 포지셔닝하지 않는다.** 포지셔닝 자체는 바꾸지 않고 검색 유입 통로만 연다. 세부 키워드 확정안은 팀 리서치 후 별도 제안(대표님 승인).

## 8. 디자인 요구사항

**절대 원칙** — AI스럽지 않을 것. 실제 데이터 사용, 더미 목업 금지.

**합격선의 정의 = 레퍼런스 7건** (카카오뱅크 서비스·앤써, 우리은행 스팟, 미래엔 AIDT, 코들 AI, 이투스 청솔, 셀펍). 취향 참고가 아니라 기준선이며, **분석 전에는 랜딩 설계에 착수하지 않는다.** 미래엔이 수치 대신 체험 링크로 신뢰를 만드는 방식은 P-D의 시각 참조 사례.

**AI스러움의 정의 (대표님 언급 기준)** — 인터랙션이 너무 일관적일 때. 목업 이미지를 그대로 노출할 때. 반대로 똑개 사이트는 섹션마다 인터랙션이 다르다.

| 실패 신호 | 합격 방향 |
|---|---|
| 모든 섹션이 같은 스크롤 | 섹션마다 인터랙션 언어가 다름 |
| 전 영역 애니메이션 | 안 넣는 곳을 의도적으로 남김 |
| 데이터 없는 카운터 | 실제 값에만, 없으면 뺌 |
| 이모지를 기능 아이콘으로 | 아이콘 세트 통일 |
| 같은 카드 반복 | 섹션마다 다른 레이아웃 |
| 목업·가짜 대시보드·로렘입숨 | 실제 데이터·실제 배포 화면 |
| 보라·인디고 그라디언트 | 브랜드 색 의도적 선정 |
| 정형 순서(Hero→기능→가격→FAQ) | 우리 서사 순서 |
| 캐릭터·마스코트 | B2B 전문성 톤 |
| 고객사 로고 월·수상 배지 등 없는 실적 연출 | 열어볼 수 있는 실물 (P-D) |

**에셋** — 포트폴리오 실화면·라이브 링크는 실물. 교육·배경·보조 이미지는 무료 에셋(기준은 출처가 아니라 완성도). 이미지 생성은 Codex/GPT.
**톤** — 레퍼런스 공통 친근체 기본, 전문성은 문체가 아니라 내용으로 증명.

| 폼/CRM | 플러그 |
| 이미지 | 클로드(레이아웃·코드) + Codex/GPT(이미지 생성) |

**보일러플레이트 커스터마이징** — orca는 블로그 자동 발행 구조로 세팅되어 있다. web/admin 분리 구조는 그대로 쓰고, admin의 등록 대상을 블로그 글에서 빌더·프로젝트로 확장한다. **블로그 발행 구조는 제거하지 않는다**(FR-7.6).

**데이터 모델** — `builders`에 `og_image`·`meta_title`·`meta_description`(FR-2.9) · `role`(admin/builder, FR-7.3). `projects`에 `link_grade`(FR-2.6) · `category`(FR-2.10) · `display_order`(FR-2.12) · `is_public`(관리자만 변경, RLS 차단, FR-7.4). 빌더-프로젝트는 **연결 테이블**(`is_owner` 플래그로 대표 1명 강제, FR-2.11). **`project_type`(실전/제작물) 필드는 두지 않는다** — 데이터에 구분이 남으면 언젠가 화면에 새어 나옴(FR-2.3).

| 계정 | 개발 중 | 최종 |
|---|---|---|
| GitHub·Vercel·Supabase | 개인 계정 | 산출물 전달 |
| GA4·서치콘솔·서치어드바이저·GTM | 우리 생성 | `jangwon@toktokhan.dev` 초대 |
| 플러그 | — | 똑개 제공 |
| 도메인 | **팀원별 개인 도메인 확보** — 검색 도구 등록·색인 확인까지 실제로 수행 | 대표님 명의 도메인으로 이관 |

**심사 기간 긴 연동 없음** → 일정 리스크 낮음.

## 11. 진행 방식

**8단계** — 수주·채널개설 → 킥오프·계정수급 → 기획 → 디자인 → 개발 → 배포·SEO → 이관 → 종료·하자보수. 각 단계 사이 **검수보고서 + 컨펌**이 관문.

**이 프로젝트 조정** — ①계정 소유 방향 반전(§10) ②안을 나열하지 않고 **과정을 설명하는 방식**으로 제출 — 검수보고서에 대안과 채택 이유를 기재 ③정산·내외부방 분리는 해당 없음.

**협업** (대표님 지정, 임의 변경 금지) — 주간 미팅 기준, 데일리 싱크 없음 · 슬랙 기본, 급한 건 전화 · 회의록은 사람이 기록.

**대표님 응답 특성** — 세부 사항에 대해 상세한 회신을 기대하기 어렵다. **되돌리기 쉬운 항목은 우리 재량으로 정하고 미결 목록에 남긴 뒤 회신 시 반영한다.** 되돌리기 어려운 항목만 확인 요청으로 올린다.

### 리스크 — 라이브 링크 확보 실패

P-A는 **열리는 링크의 수**에 전적으로 의존한다. 임계값과 대응을 미리 정한다.

| "상" 등급 이상 확보 | 판정 | 대응 |
|---|---|---|
| 8건 이상 | 정상 | 계획대로 그리드 구성 |
| 5~7건 | 주의 | 그리드 → 소수 정예 서술형. 프로젝트당 분량을 늘려 건수를 깊이로 상쇄 |
| 4건 이하 | 위험 | ①일하는 방식(FR-4) 비중 확대로 무게중심 이동 ②"하" 등급(영상) 허용 확대 ③대표님께 범위 조정 협의 요청 |

**판정 시점 — 1주차 콘텐츠 트랙 종료 시.** 4건 이하이면 즉시 검수보고서로 공유하고 컨펌 후 진행한다. 2주차 이후에 발견되면 되돌릴 수 없다.
