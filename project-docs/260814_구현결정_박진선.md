### 1. P-01 카피 — 신규 작성본 B안 전체 채택

**판단**: 「`카피후보_박진선_P01_v1.md`」의 **B안(신뢰 중심) 8섹션 + CTA 전문**을 채택한다. 기획-2안은 폐기한다.

| 항목 | 내용 |
|---|---|
| 시점 | **전 문장 방문자 시점으로 통일.** "우리가 이렇게 합니다"가 아니라 "당신이 이걸 확인할 수 있습니다" |
| 참조 범위 | 기획안 · PRD · 확정문서. **팀 공유 후보집(`archive/`)은 미사용** — 기존 문장에 영향받지 않은 상태로 새로 쓰는 것이 작성 목적이었다 |
| 관리 방식 | `apps/web/content/p01-copy.ts` 한 파일. 섹션별 상수로 구조화하고 컴포넌트는 문장을 직접 갖지 않는다 |
| 적용 범위 | 히어로만 화면 연결. **02~08은 상수만 준비**하고 조립 시 `p01Copy`에서 꺼내 쓴다 |

**A안(확인 중심)을 쓰지 않은 이유** — A안은 "다 열어볼 수 있다"는 인상이 라이브 링크 물량에 전적으로 의존한다. PRD §12 리스크대로 "상" 등급이 8건에 미달하면 카피가 근거보다 앞서 나간다. 물량 판정 전에는 물량과 무관하게 성립하는 B안이 안전하다. **판정 결과가 8건 이상이면 A안 재검토 대상이다.**

### 2. 히어로 카피 — FR-1.7 미확정 상태에서 임의 결정

**판단**: 회신을 기다리지 않고 **본사 관계 표기 최소 수위**로 진행한다.

| 항목 | 내용 |
|---|---|
| 본사 표기 | **본사를 주어로 세우지 않는다.** "본사가 보증한다" 취지의 문장을 두지 않는다 |
| 신뢰의 근거 | 조직 관계가 아니라 **일하는 방식 · 검증 절차**로 구성한다 (확정 소구점 1·3) |
| 전제 | **발주사 확인 후 교체를 전제한 잠정 결정이다.** FR-1.7 회신과 발주사 컨펌(POL-13) 시 교체한다 |

**교체 비용을 미리 낮춰 둔 방식** — 카피가 상수 파일 한 곳에 모여 있어 회신이 오면 그 파일만 바꾸면 된다. 컴포넌트에 문장이 박히지 않으므로 어디까지가 컨펌 대상인지 추적이 끊기지 않는다.

**FR-1.7이 어느 쪽으로 회신되든 문장이 무효가 되지 않는다.** A안(관계 명시)이면 표기를 더하는 작업이고, B안(별도 브랜드)이면 그대로 둔다. 종전 카피는 B안 회신 시 근거를 잃는 구조였다.

**판단**: 히어로에 배경 영상과 PAUSE 컨트롤을 **두지 않는다.**

## 스키마 구현 결정 (2026-08-16)

`packages/supabase/migrations/0002_ai_builder_group.sql` 작성 시 판단한 것이다.
기준은 『데이터 모델』(ABG-DM-006) v1.2이며, 테이블 8종·RLS·인덱스를 그대로 옮겼다.

### 1. 컬럼 단위 UPDATE 제한 — GRANT 대신 RLS, 일부 미구현

**문서**: §4.2가 빌더의 UPDATE에서 특정 컬럼을 제외하라고 규정하고, §4.3이 *"`GRANT UPDATE (컬럼목록)` 권장. DB가 강제"* 로 방법을 지정한다.

| 테이블 | 빌더가 못 바꿔야 하는 컬럼 |
|---|---|
| `builder` | `slug` · `cohort` · `is_public` · `is_pinned` · `pin_order` |
| `project` | `slug` · `is_public` · `sort_order` |

**판단**: **GRANT를 쓰지 않고 RLS 정책으로 간다.** Supabase에서 admin과 builder는 **모두 `authenticated` 롤**이라 롤 단위 GRANT로 둘을 가를 수 없다. 문서가 지정한 방법이 이 환경에서 그대로 성립하지 않는다. 대신 `is_admin()` · `my_builder_id()` 를 조건으로 하는 UPDATE 정책으로 **권한 범위(누가 어느 행을)** 를 강제한다.

> ⚠️ **컬럼 단위 제한은 이번 마이그레이션에 구현되지 않았다.**
> Postgres RLS는 행 단위다. `WITH CHECK`는 NEW 행만 보고 OLD를 참조하지 못해 *"이 컬럼 값이 안 바뀌었는지"* 를 검사할 수 없다. 남은 방법은 `BEFORE UPDATE` 트리거인데 데이터모델 문서에 정의돼 있지 않아 만들지 않았다.
>
> **현재 노출도** — 쓰기는 service role(관리자 서버 액션) 경유이고 빌더 셀프 편집 화면(A-06)이 아직 없어 실제 경로는 열려 있지 않다. **A-06 착수 전에 반드시 닫아야 한다.**
>
> **팀장 확인 필요** — 트리거를 추가할지, 서버 액션 필드 필터링(§4.3 "보조")만으로 갈지. 후자면 `REQ-N-011`(*"프론트엔드 은닉으로 대체하지 않는다"*, P0)과 충돌한다.

### 2. `project_builder` 익명 SELECT 차단 — 서버 조회 전제

**문서대로 `✕`로 구현했다.** 임의로 열지 않았다.

**전제**: 공개 화면(P-01 섹션 4 · P-04)의 담당 빌더 표기는 **서버 컴포넌트에서 서버 측 키로 조회**한다. anon 키로는 이 조인이 읽히지 않는다.

> **팀장 확인 필요** — 문서 §4.2에 비대칭이 있다. 바로 아래 `project_category`는 익명에게 *"공개 프로젝트분"* 을 허용하는데 `project_builder`만 전면 차단이다. **분류 배지는 anon으로 읽히고 담당 빌더는 안 읽힌다.** 의도된 것인지, 표 작성 시 누락인지 확인이 필요하다. FN-C01-04(*"OOO 외 N명"*)가 공개 카드의 필수 표기이므로 영향이 있다.

### 3. 시딩하지 않은 것 — `category` 초기 9건

§3.4가 `axis`·`name` 9건을 확정했으나 **`slug` 값을 정의하지 않았다.** slug는 URL이자 발행 후 변경 금지 대상(`REQ-N-013`)이라 임의 생성이 불가하다. 테이블만 만들고 9건은 SQL 주석으로 남겼다. **slug 확정 후 별도 시드로 넣는다.**

### 4. 넣지 않은 제약 2종

| 항목 | 근거 |
|---|---|
| 길이 상한 CHECK (`display_name` 40 · `summary` 120 · `bio` 200 · `title` 60) | §8이 *"초과 시 저장을 막지 않고 경고만 한다"* 로 규정. CHECK로 걸면 문서 위반 |
| 카드 분류 배지 "최대 2개" 제약 | §3.5가 C-01 **표기 규칙**으로 규정했지 저장 제한으로 두지 않음 |

### 5. 슬러그 문자 규칙 — 패턴 제약을 두지 않는다

데이터모델 문서는 slug에 `UNIQUE`와 "발행 후 변경 금지"만 규정하고 **문자 규칙을 정의하지 않았다.** IA §6.1이 *"자연어(한글) 허용"* 이므로 ASCII 전용 같은 패턴 CHECK를 걸면 안 된다. `insight`에는 **예약어 CHECK만** 두었다.

```sql
constraint insight_slug_not_reserved
  check (slug not in ('before', 'process', 'people'))
```

### 6. 기타

| 항목 | 결정 | 근거 |
|---|---|---|
| `posts` 테이블(0001) | **유지.** 드롭하지 않음 | 데이터모델에 없어 앞으로 쓰지 않을 뿐. 정리는 별도 작업 |
| 열거값 CHECK | `status`(course·insight) · `link_grade` · `name_type` · `insight.category` **전부 추가** | 문서가 값을 나열한 것은 그 값만 허용한다는 의미로 해석 |

## 문서 간 충돌 — 슬러그 한글 허용 (2026-08-16)

**상황**: 슬러그의 한글 허용 여부가 문서마다 반대다.

| 문서 | 규정 |
|---|---|
| IA §6.1 | *"자연어(한글) 허용. 발행 후 변경 금지"* (`REQ-N-013`) |
| IA §4 주석 | *"글 슬러그는 자연어 한글을 쓰므로(`REQ-F-092`)"* |
| `REQ-F-012` | 프로젝트 슬러그는 검색어와 일치 — 예: `/portfolio/에어로케이` |
| CLAUDE.md 코드 규칙 | *"슬러그는 자연어 한글을 쓴다(`REQ-N-013`). 발행 후 변경 금지"* |
| **PRD `FR-8.5`** | ***"슬러그는 영문 키워드 조합 자동 생성. 한글 슬러그 금지 — 공유·색인 시 인코딩 문제"*** |

**판단**: **한글 허용이 맞다.** 확정문서(IA·요구사항)가 우선순위 3위이고 PRD는 5위다. 브라우저가 non-ASCII를 퍼센트 인코딩하지만 표시할 때는 디코딩하므로 `FR-8.5`가 든 근거도 실무상 약하다.

**PRD `FR-8.5`가 갱신 대상이다.** 이번 스키마는 slug에 문자 패턴 제약을 두지 않았으므로 한글이 그대로 들어간다.
