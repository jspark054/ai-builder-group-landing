## 0. 프로젝트 개요

빌더(바이브코더)들의 포트폴리오를 노출하고 **"바이브코딩 외주 전문 개발사"**로 포지셔닝해, 외주 문의(리드)를 수집하는 랜딩 페이지입니다.

한 줄 포지셔닝: **검증된 바이브코더를, 조직이 보증해서 붙여준다.** 업체처럼 실체를 감추지 않고, 개인처럼 혼자 두지 않습니다.

## 2. 배경 · 목적 · 포지셔닝

### 2-1. 브랜드 구조

| 항목 | 내용 |
|---|---|
| 상위 브랜드 | AI 빌더 그룹 |
| 하위 축 1 | 빌더 스쿨 — 수익화 가능한 직무 교육 |
| 하위 축 2 | 크루/커뮤니티 — 무료 세미나·수료생 스터디 (구상 단계) |
| 현재 포지셔닝 | 바이브코딩 외주 전문 개발사 |
| 장기 방향 | AX 컨설팅 확장 (현재는 바이브코딩 키워드 집중) |
| 목표 흐름 | 브랜드 노출 → 리드 수집 → 교육생에게 일감 배정 |

**교육 라인업이 여러 개라는 사실 자체가 소구점입니다.** 준비 중인 과정(바이브코딩 · AX 컨설턴트 · AI 네이티브 창업)은 단발성 강의가 아니라 직무별 과정을 갖춰가는 조직임을 보여주며, 이것이 "이 조직이 계속 존재할 것"이라는 신뢰의 근거가 됩니다.

> **커뮤니티는 이번 범위에서 제외합니다** — 없어서가 아니라 아직 이르기 때문입니다. 현재 1기가 진행 중이라 수료생·세미나 이력이 축적되지 않았고, 지금 만들면 빈 페이지가 됩니다. 정보구조와 데이터 모델에 **자리만 확보**해 두고, 1기 수료·세미나 개최 후 채웁니다.

### 2-2. 똑똑한개발자 본사와 다른 시장

본사와는 타깃·규모·소구점이 다른 별개 서비스입니다.

| | 똑똑한개발자 본사 | AI 빌더 그룹 |
|---|---|---|
| 인력 | 경력 개발자·디자이너·기획자 | 바이브코더 |
| 프로젝트 규모 | 크고 다인원 | 작고 빠름 |
| 클라이언트 | 예산·조직을 갖춘 곳 | 큰 개발사를 쓰기 어려운 곳 |
| 무기 | 축적된 경력·실적 | 바이브코딩의 속도·규모 적합성 |

> **저가를 앞세우지 않습니다.** 가격을 무기로 내걸면 개인 프리랜서와 같은 경쟁이 되어 조직 운영 쪽이 불리합니다. 소구점은 **"이 규모에는 이 방식이 맞다"**는 적합성입니다.

## 3. 핵심 전략 — 세 개의 축

### 3-1. 시장의 문제 — 클라이언트가 구분하지 못한다

발주를 고민하는 클라이언트의 어려움은 두 갈래이고, 모두 **"가려낼 수 없다"**로 모입니다.

| 상대 | 문제 |
|---|---|
| 업체군(TenAI 등) | 서로 비슷해 보여 구분되지 않음 |
| 개인 바이브코더 | 검증할 방법이 없음 (껍데기를 포트폴리오로 위장 가능) |

### 3-2. 세 개의 축 — 각 축이 다른 질문에 답한다

| 축 | 답하는 질문 | 증명 방법 |
|---|---|---|
| 포트폴리오 | "실제로 만들 수 있나?" | 라이브 링크(열어보면 5초면 드러남) + 담당 빌더 특정 |
| 교육 | "실력이 어디서 왔나?" | 수료 과정·커리큘럼 + 과정 라인업 |
| 일하는 방식 | "맡기면 어떻게 관리되나?" | 8단계 프로세스·검수보고서·컨펌 + 역할 분리된 팀 + 똑빌더 |

**세 축은 서로를 보증합니다.** 포트폴리오만 있으면 위조 의심을 벗지 못하고, 교육만 있으면 교육 홍보로 읽히고, 일하는 방식만 있으면 말뿐인 프로세스가 됩니다. 세 축의 **연결 자체가 요구사항**입니다.

> 축의 명칭은 "일하는 방식"입니다. 도구명(똑빌더)은 외부에 알려져 있지 않으므로, 전달할 메시지는 **"AI 시대에 최적화된 방식으로, AI와 함께 일한다"**이며 똑빌더는 그 증거물입니다.

### 3-3. 의사결정 여정과 사이트 대응

| 단계 | 클라이언트 상태 | 이탈 요인 | 사이트 대응 |
|---|---|---|---|
| 인지 | "바이브코딩으로 되나?" | 검색에 안 뜸 | SEO/GEO (§10) |
| 비교 | 후보 3~4곳 나열 | 다 비슷해 보임 | 선택 기준 섹션 (§6) |
| 검증 | "진짜 만들 수 있나?" | 껍데기 의심 | 빌더·포트폴리오·교육·일하는 방식 (§7) |
| 문의 | "얘기나 해볼까" | 폼이 번거로움 | 플러그 폼 (§9) |

|---|---|---|:---:|

**모든 축에서 충족되는 경쟁사가 없습니다.** 특히 축 5(검색·AI 노출)와 축 6(이관 정책)은 시장에서 비어 있어, 명시하는 것만으로 차별점이 됩니다.

### 4-3. 예상 반론과 대응

| 클라이언트 의심 | 대응 |
|---|---|
| "교육생이 만드는 것 아닌가?" | 교육은 이력이 아니라 **품질 균일성의 근거**. 같은 방법론으로 훈련되어 편차가 작음 |
| "바이브코딩 코드, 유지보수 되나?" | 저장소 이전(히스토리 유지)·키 점검·산출물 일체 전달·인수인계까지가 프로세스에 포함 |
| "담당 빌더가 떠나면?" | 팀장이 단일 창구, 역할 분리로 조직이 인수 |

## 5. 정보구조 (IA)

```
/                        랜딩
│
├─ /builders             빌더 리스트         ← 포트폴리오 입구
│  └─ /builders/<이름>    빌더 상세          ← 프로젝트 인라인 전개
│
├─ /portfolio/<프로젝트>  프로젝트 개별 URL   ← 검색 진입점
│
├─ /courses              교육 과정
│  └─ /courses/<과정>     과정 상세          ← 수료 빌더 목록 포함
│
├─ (/community)          커뮤니티 — 2차 (자리만 확보)
│
├─ /process              일하는 방식
│
└─ /contact              문의 — 플러그 폼 임베드
```

**뎁스는 2단을 넘지 않습니다.** 빌더 상세에서 프로젝트가 클릭 없이 전부 보이고, `/portfolio/<프로젝트>`는 검색·AI 인용을 위한 독립 진입점입니다.

**블로그/인사이트는 이번 범위에서 제외합니다.** 사이트의 핵심 축은 포트폴리오·교육·일하는 방식 세 가지이며, 블로그는 이 신뢰 구조 안에서 별도로 겉돌 여지가 있어 제외하는 편이 사이트 논리를 더 선명하게 합니다. 향후 AI 검색 노출용 콘텐츠가 필요해지면 2차로 인사이트 페이지를 추가할 수 있도록 구조만 열어 둡니다.

### 5-1. 페이지 간 연결

체인이 끊기지 않도록 아래 3개 경로는 양방향으로 연결합니다: ①프로젝트 ↔ 담당 빌더 ②빌더 ↔ 수료 과정 ③프로젝트·빌더 → 문의(관심 대상 파라미터 부착).

### 5-2. 탭도 고유 URL을 가진다

교육 과정·포트폴리오 필터 등 탭 전환 요소는 각각 고유 URL을 갖습니다(`/courses/바이브코딩` 등). 화면상 탭 전환이라 클릭 깊이는 늘지 않지만, GA4 개별 페이지뷰 집계·독립 색인·링크 공유가 가능해집니다.

### 5-3. 중복 콘텐츠 처리 — canonical 미적용

빌더 페이지에는 프로젝트 **요약**(제목·1~2줄·썸네일·라이브 링크)을, `/portfolio/<프로젝트>`에는 **전문**(문제→해결→결과·실화면·담당 빌더)을 싣습니다. 두 페이지의 분량과 목적이 달라 중복 문제가 발생하지 않으므로 canonical은 적용하지 않으며, 이를 통해 프로젝트 개별 페이지가 독립된 검색 진입점으로 기능하도록 합니다.

## 6. 화면 설계

### 6-1. 랜딩 구성 방향 — 선택 기준 제시형

시장의 문제가 "클라이언트가 가려낼 수 없다"이므로, **"이렇게 고르세요"라는 판단 기준을 먼저 제시**하고 그 기준으로 우리를 보게 하는 구성을 채택합니다. 이 방식은 비교표 형식이라 AI 검색 인용에도 유리합니다.

### 6-2. 랜딩 섹션 구성

섹션마다 스크롤 인터랙션을 다르게 하여 "AI스러움"을 방지합니다(§11). 인터랙션은 디자인 단계에서 레퍼런스 분석 후 확정합니다.

| # | 섹션 | 답하는 질문 |
|---|---|---|
| 1 | 히어로 | "여긴 뭐 하는 곳인가" |
| 2 | 문제 제기 | "왜 고르기 어려운가" |
| 3 | 선택 기준 | "어떻게 골라야 하나" |
| 4 | 빌더 | "누가 만드나" |
| 5 | 포트폴리오 | "무엇을 만들었나" |
| 6 | 교육·조직 | "실력 출처와 조직" |
| 7 | 일하는 방식 | "맡기면 관리되나" |
| 8 | 문의 | "얘기해 볼까" |

**빌더(4) 섹션이 포트폴리오(5)보다 앞섭니다** — 사이트 정체가 "바이브코더들의 포트폴리오"이므로 사람을 먼저 보여줍니다. 문제 제기(2) 섹션은 외주 사고 사례를 나열하지 않고 "선택지가 많은데 구분이 안 된다" 수준으로 절제해, 외주 자체에 대한 부정적 인상을 주지 않습니다.

### 6-3. 하위 페이지

| 페이지 | 구성 |
|---|---|
| `/builders/<빌더>` | 프로필 → 프로젝트 인라인 전개 → 문의 CTA |
| `/portfolio/<프로젝트>` | 문제→해결→결과 + 실화면 + 라이브 링크 + 담당 빌더 → 문의 CTA |
| `/courses/<과정>` | 커리큘럼 → 수료 빌더 목록 → 빌더 프로젝트 연결 |
| `/process` | 일하는 방식(똑빌더) + 8단계 프로세스 |

모든 하위 페이지 끝에는 관심 대상을 파라미터로 실은 문의 CTA를 배치합니다(§9).

## 7. 포트폴리오 구조

### 7-1. 콘텐츠와 링크가 함께 필요하다

| 요소 | 역할 | 없을 경우 |
|---|---|---|
| 콘텐츠+이미지 | 검색에 걸리는 실체 | 프로젝트 단위 검색에 노출 안 됨 |
| 바로가기 링크 | 검증 수단 | 껍데기 포트폴리오와 구분 안 됨 |

목적이 달라 둘 중 하나로 대체할 수 없습니다.

### 7-2. 포트폴리오 소스 — 2층 구조

| 층 | 내용 | 규모 |
|---|---|---|
| 실전 사례 | 에듀셀파·동행케어·카본벨트 | 3건 |
| 빌더 제작물 | 빌더 개인 작업물 | 13명 × 1건 이상 |

두 층을 함께 쓰는 이유는, 실전 사례의 라이브 링크 공개가 제한되더라도 사이트가 성립하도록 하기 위함입니다. 포함 대상은 바이브코딩 건으로 한정하며, 다인원 투입 건은 제외합니다.

### 7-3. 선별 기준 — 포트폴리오가 AI스러우면 안 된다

"AI를 잘 쓰는 곳은 다르다"가 우리 주장이므로, 포트폴리오가 AI 티를 내면 주장이 무너집니다. 라이브 링크는 수준이 낮으면 스크린샷보다 해로울 수 있어 선별이 필요합니다.

| 판정 | 처리 |
|---|---|
| 통과 | 라이브 링크 그대로 노출 |
| 보완 가능 | 위반 항목만 수정 후 포함 |
| 미달 | 링크 없이 콘텐츠만, 또는 제외 |

**선정 절차**: 팀 리스트업·1차 판정 → 클라이언트 공유 → 클라이언트 최종 확인 → 확정본 콘텐츠 제작. 1차 판정 기준은 §11의 체크리스트입니다.

### 7-4. 프로젝트 카드 구성 + 링크 등급

카드 요소: 프로젝트명 · 설명(문제→해결→결과) · 실제 화면 이미지(alt·파일명·OG 세팅) · 바로가기 링크 · 담당 빌더·수료 과정.

| 링크 등급 | 형태 | 검증력 |
|---|---|---|
| 최상 | 실운영 서비스 | 완전한 증명 |
| 상 | 배포 결과물(Vercel) | 실제 동작 확인 |
| 중 | GitHub | 비개발자에겐 약함 |
| 하 | 동작 영상 | 정지 이미지보다 나음 |
| 최하 | 스크린샷 | 위조 가능 |

"상" 등급까지는 검증 소구점이 성립합니다. 실전 사례 링크가 제한될 경우 "하"(영상)로 대체합니다.

### 7-5. 빌더 표기

빌더의 표기명(실명/닉네임)과 이미지(실사/아바타/없음)는 개인이 선택하며, 이력·수료 과정·기수는 공통으로 노출합니다. 이미지가 없어도 카드가 깨지지 않도록 대체 표시(이니셜)를 준비합니다. 표기 방식의 혼재는 오히려 "균일한 그리드 = AI 티"를 자연스럽게 완화합니다.

### 7-6. 일하는 방식 — 8단계 프로세스

전달 메시지는 **"AI 시대에 최적화된 방식으로, AI와 함께 일합니다"**이며, 이를 실물로 뒷받침합니다.

```
수주·채널개설 → 킥오프·계정수급 → 기획 → 디자인 → 개발 → 배포·SEO → 이관 → 종료·하자보수
```

각 단계 사이에 검수보고서와 컨펌 관문이 있습니다. `/process` 페이지에 8단계를 설명하고, 똑빌더는 게스트 계정으로 직접 사용해 본 뒤 이미지/다이어그램 형태로 노출합니다.

## 10. SEO / GEO

### 10-1. 키워드 전략 — 상업 키워드가 비어 있다

"바이브코딩 견적/외주/개발사/홈페이지 제작" 등 상업 키워드는 현재 교육 수강료·위키·기사가 상위를 차지하고 있어 **실제 개발사의 진입 공백**이 큽니다. 인접 시장(앱개발·MVP)은 위시켓·크몽으로 포화 상태이므로, **"바이브코딩" 상업 키워드에 집중**합니다.

키워드 3계층: 메인(바이브코딩 개발사·외주·견적·홈페이지 제작) / 확장(앱개발·MVP·노코드) / 장기(AX 컨설팅·AI 전환).

### 10-2. GEO — 자사 사이트만으로는 부족하다

AI 검색의 브랜드 언급은 상당 부분 제3자 페이지(리스티클·비교글)에서 발생합니다. 온사이트 대응으로 포트폴리오·빌더·교육을 **자기완결 블록(2~3줄)과 비교표 형식**으로 구성하고, 오프사이트 외부 채널 노출은 발행 후 운영 과제로 병행할 것을 제안합니다.

### 10-3. 테크니컬 체크리스트

- 구글 서치콘솔·네이버 서치어드바이저·GA4·GTM 생성 → `jangwon@toktokhan.dev` 초대
- sitemap.xml · robots.txt(개발용 전체 차단 해제 확인) · rss.xml · llms.txt
- 구조화 데이터: Organization + Article(프로젝트 상세) + FAQPage
- 페이지별 메타 · 자연어 슬러그 · 이미지 alt·압축
- 색인 확인(`site:도메인`)

**메타 길이 기준**: title 40자 이내(핵심 키워드는 앞 15자 이내 배치), description 80~110자.
예) `바이브코딩 외주 전문 개발사 | AI 빌더 그룹`

### 10-4. URL 트래킹

외부 유입(UTM)과 내부 구조(탭·필터의 개별 URL)를 구분해 측정합니다. GA4 이벤트 최소 3종: 문의 폼 진입·제출·포트폴리오 링크 클릭.

- 상투적 카피는 사람이 최종 수정한다
- **전 페이지 동일 인터랙션 반복을 피하고 섹션마다 다르게 한다**

## 13. 일정 · 진행 방식 (3주)

### 13-1. 주차별 계획 (개발·콘텐츠 트랙 병행)

| | 개발 트랙 | 콘텐츠 트랙 | 단계 종료 |
|---|---|---|---|

| W2 | 랜딩·포트폴리오·빌더·교육·프로세스·어드민 | 프로젝트 상세 콘텐츠·실화면 정리 | 개발 검수보고서 → 컨펌 |
| W3 | 플러그 연동·SEO·최종 QA | 워딩 최종 수정 | 배포 → 이관 → 종료 보고 |

콘텐츠 트랙을 별도로 관리하는 이유는, 자료 수급·선별이 일정을 좌우하는 가장 큰 변수이기 때문입니다. W1에 선별을 완료해 물량 확보 여부를 조기에 파악합니다.

**착수 즉시 진행**: 똑빌더 게스트 사용·구조 파악 · 플러그 가입 후 파라미터 지원 확인 · 빌더 제작물 13건 선별 · 개발사 포트폴리오 사이트 조사 · 교육 에셋 요청(동화님) · SEO 계정 생성.

### 13-2. 2차로 이관하는 항목

빌더 개인별 권한 · 커뮤니티/세미나 페이지 · 누적 수치 노출 · 블로그 · 고도화 인터랙션. 1차에서는 정보구조에 경로를, 데이터 모델에 엔티티를 미리 정의해 자리를 확보합니다.

### 13-3. 성과 측정 (리드 기준)

발행 시점(SEO·색인·메타 완료) → D+2주(색인 페이지 수) → D+1개월(키워드 순위·경로별 세션) → D+2~3개월(문의 폼 제출 수·포트폴리오 경유 비율). 목표 수치는 킥오프에서 합의합니다.

### 14-3. 컨펌 요청

본 기획안은 프로젝트의 화면·기능 범위를 정의하며, 여기서 확정된 범위가 이후 진행의 기준선이 됩니다. 검토 후 **컨펌** 회신을 주시면 확정된 범위를 기준으로 디자인 단계에 착수합니다.

다음 주 화요일 디자인 시안 목표에 맞춰, §14-2 확인 요청 3건은 각 항목의 진행 방안대로 먼저 작업을 시작하겠습니다. 회신 주시면 즉시 반영하겠습니다. 특히 **1번(라이브 링크 노출 동의)**은 포트폴리오 구성에 직접 영향이 있어 가능한 이른 회신을 부탁드립니다.
