## 0. 결정 순서

`01 §7.4`의 권장 순서를 그대로 따릅니다. **위에서부터 정해야 아래가 정해집니다.**

```
① A-1 권한 구조        ← 일정 전체가 여기서 결정됨
② A-2 문의 출처 추적    ← 기존 전제가 무효화되어 대안 확정 필요
③ A-3 → A-4 화면 순서·분리   ← 화면 설계 착수 조건
④ G-1~3 개발 블로커     ← 코드를 못 짜는 것들
⑤ A-5 산출물 수렴       ← 디자인 검수 이전
⑥ B군 범위·일정         ← ①의 결과에 따라 가용 공수 확정
⑦ C군 발주사 확인       ← 미팅 안건으로 이관
```

### ⚠️ 빌더 인원 정정 — 13명 → 12명

**1인 포기로 12명입니다.** 문서 3곳에 `1기 13명`이 남아 있어 v2.0에서 고쳐야 합니다.

| 문서 | 위치 |

목록 구조로 취급한다"*로 못박아 뒀기 때문입니다. **다만 인원이 늘고 주는 것이 확인됐으므로
그 문장의 근거가 더 강해졌습니다.**

**A-3 → 포트폴리오 우선.** 사유는 *"아직 빌더의 경력이 부족해 신뢰도 저하 우려"*입니다.
**근거가 기록돼야 합니다** — 나중에 빌더 경력이 쌓이면 재검토할 수 있는 판단이기 때문입니다.

**A-4 → 단일 목록 + 순서 배치.** 실전 사례와 빌더 제작물을 한 목록에 두되
**노출 순서를 조정할 수 있어야 합니다.** `REQ-F-063`(정렬 순서 수동 조정)이 이미 있으나,
**유형이 섞인 상태에서의 순서 정책**이 새로 필요합니다.

### ⚠️ A-2 — 확정 사항이 뒤집혔습니다

**`01 §6 REQ-C-002`가 *"플러그는 URL 파라미터를 수신하지 못한다 (실측 확인)"*로 `확정` 상태입니다.**

**가이드 문서를 받으면 확인할 것**

### ⚠️ A-5 — 요구사항이 아닌 것이 요구사항에 들어와 있습니다

**`REQ-C-010`은 두 부분으로 되어 있고, 성격이 다릅니다.**

| 부분 | 내용 | 판정 |
|---|---|---|
| **본문** | *"주력 1~2안을 선정하고 나머지와 비교하여 채택 사유를 설명하는 형식으로 제시한다"* | ✅ **유지.** 녹취록 16:21 · 17:19 근거 확실 |
| **보충 + 안건 12** | *"수행팀은 6인이며 전원이 각자 산출물을 제작한다 … 내부에서 주력을 선정하는 절차가 필요하다"* | ❌ **내린다** |

**보충을 내리는 이유가 둘입니다.**

**① 수행사 내부 운영이지 발주사 요구가 아닙니다.**
누가 산출물을 만들고 어떻게 고르는지는 **우리 팀 진행 방식**입니다.
요구사항 정의서는 *"무엇을 만드는가"*를 적는 문서입니다.

**② "6인 = 6개 시안" 연결이 근거와 어긋납니다.**

`00 근거감사보고서 §상충-2`가 직접 밝혀 놓았습니다.

> 6개 시안은 **개발사가 제시한 것이 아니라 발주처 담당자(이호영)가 직접 AI로 만들어 스스로 고른 것**이고,
> 대표가 *"이런 방법도 좋은 방법"*이라 한 것은 그 상황을 설명한 맥락이다.

**대표가 말한 "6개 시안"은 다른 프로젝트의 클라이언트가 만든 것입니다.
우리 팀이 6인인 것과 아무 관련이 없습니다.**
`01 §6` 보충이 **숫자가 같다는 이유로 둘을 연결**했는데, 같은 문서 세트의 근거감사가
이미 아니라고 결론 낸 사안입니다.

### G-3b — 안전한 기본값으로 시작한다

**조인 테이블에 `is_owner` 플래그를 두고, 대표 1인만 편집한다.**

**"결정을 미룬다"가 아니라 "좁게 시작하고 나중에 완화한다"이다.** 방향에 따라 비용이 다르기 때문이다.

| 방향 | 비용 |
| --- | --- |
| **좁게 시작 → 나중에 열기** | **RLS 조건 한 줄 완화. 거의 공짜** |
| 넓게 시작 → 나중에 조이기 | 공동 건이 쌓인 뒤 **대표를 사람이 손으로 지정**해야 함 |

**디자인·개발 완료 후 재검토한다.** 그때 *"다 열어도 되겠다"*로 판단되면
RLS 조건만 지우면 되고, 화면에서는 `A-06`의 잠금 표시를 제거하면 된다.

| 층 | 대표 1인 편집 시 |
| --- | --- |
| 스키마 | `project_builder.is_owner` 컬럼 1개 |
| 권한 | RLS `UPDATE` 조건에 `is_owner = true` |
| 화면 | `A-06`에서 참여 건에 🔒 표시 (기존 잠금 체계 재사용) |

> **G-3d 확정의 파생** — 한 프로젝트가 여러 빌더 페이지에 뜨므로
> `P-06`의 프로젝트 건수 집계와 `POL-02`(프로젝트 0건 빌더 비노출) 판정에

### I-5. 규칙 적용 완화 — 방향성 공유 완료

시안 비교와 위 4건 결정으로 방향성(확정 소구점 3건 · POL-11① · 시안2 인터랙션 방향)이
클라이언트에게 직접 검증됐다. 이제 각 팀원이 맡은 화면의 **카피와 디자인 세부 표현에는
개인 스타일을 허용**한다 — 방향성만 지키면 표현 방식까지 하나로 맞출 필요는 없다.

**완화되는 것과 유지되는 것을 구분한다.** "전부 느슨해졌다"로 오독하지 않도록 표로
명시한다.

| 구분 | 정책 | 이번 결정 |
|---|---|---|
| 완화 | **POL-13 4단 레지스터(R1~R4)** — "네 레지스터 외 혼용은 불합격 사유" 규정 | 강제 불합격 사유에서 제외하고 **가이드라인으로 낮춘다**. 톤을 어떻게 표현할지는 작성자 재량 |
| 완화 | I-3의 시안1 카피 채택 여부 | 참고 후보일 뿐 강제 채택이 아니다 |
| **유지** | **POL-11①**(AI스러움 4항목, 발주사 지목·반려 사유) | **오히려 강화됨.** I-2에서 클라이언트가 직접 재검증했다 — 완화 대상 아님 |
| **유지** | **POL-01**(수치 노출 금지) | 사실 근거가 걸린 규칙 — 유지 |
| **유지** | **POL-09**(콘텐츠 공개 범위) | 계약·법적 사항과 연결 — 유지 |

### I-7. 카피 미확정 재선언 (v3.4 · 2026-08-11)

I-3에서 "채택 검토"로만 다뤘던 카피 상태를 **더 명확히 정정한다.**

| ID | 안건 | **결정** |
|:---:|---|---|
| **I-7** | **카피 확정 상태 재정의** | ✅ **모든 카피는 확정이 아니다.** 기존 "확정 카피"(카피 전략 보고서 §"확정 카피 요약")를 **기획-2안**으로, 시안1 원문(§11)을 **기획-1안**으로 재표기한다. 화면을 만드는 팀원이 둘 중 하나를 쓰거나, 섞거나, 새로 써서 결과물을 제출한다 |

**I-2·I-3과의 관계** — I-2(시안2 디자인 채택)는 그대로 유지된다. 이번 결정은 **카피에만**
적용된다. 디자인 방향(섹션별 인터랙션)과 카피 문구(기획-1안/기획-2안)는 서로 다른 축이므로,
디자인은 시안2로 확정하고 카피는 두 안 다 후보로 열어두는 조합이 모순되지 않는다.

**바뀌는 것과 안 바뀌는 것**

| 구분 | 내용 |
|---|---|
| 바뀜 | "확정 카피"라는 표현을 문서 전체에서 쓰지 않는다. 기획-1안/기획-2안 두 후보로 병기한다 |
| 바뀜 | POL-13 "최종 확정 → 발주사" 앞 단계(수행사 내부 확정)가 사라진다 — 팀원이 바로 발주사 컨펌 단계로 제출할 문안을 고른다 |
| 안 바뀜 | POL-13의 **발주사 최종 승인 절차 자체**는 유지된다 |
| 안 바뀜 | 확정 소구점(§2.4, 3건)은 카피가 아니라 전략 프레임워크이므로 그대로 확정 상태를 유지한다 |
| 안 바뀜 | POL-01·POL-09·POL-11①처럼 사실/법적 근거가 걸린 정책은 계속 유지된다(I-5) |
