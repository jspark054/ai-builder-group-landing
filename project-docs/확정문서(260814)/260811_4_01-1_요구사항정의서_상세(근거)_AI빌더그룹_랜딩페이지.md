### 목적

『요구사항 정의서』(ABG-REQ-001)에 정의된 각 요구사항의 도출 근거, 원문 인용, 해석 판단, 정정 이력을 요구사항 ID 단위로 기술한다.

본 문서는 다음 상황에서 참조한다.

- 요구사항의 배경이나 의도가 불분명할 때
- 요구사항 변경을 검토할 때 원래 근거를 확인할 때
- 검수 시 판정 기준의 출처를 확인할 때

### 근거의 층위

```
1차   1차 고객 미팅 녹취록 (2026-08-04, 약 38분)      ← 최우선
       │  정리
2차   회의록 (2026-08-04)                              ← 단독 근거로 사용하지 않음
       │  해석
3차   기획서 4부 · 팀원 개별 PRD 6부
       │  병합
4차   요구사항 정의서 v1.0
```

**녹취록은 발언을 기록하지만 그 발언이 요구인지 사례 설명인지는 기록하지 않는다.** 3차·4차 문서에서 이로 인한 오독이 8건 발생했으며, 원문 대조를 통해 정정했다(§4).

### 표기 규칙 (문서 공통)

| 표기 | 용도 |
|---|---|
| **굵게** | **판정 · 금지 조건에만 사용한다.** "~하지 않는다", "~시 불합격", "미노출", "차단" |
| `코드` | 수치 · 등급 · 경로 · 속성값 |

굵게 표시된 문장은 **검수 시 판정 대상**이다. 강조 목적으로 사용하지 않는다.

### 근거 유형 표기

| 표기 | 정의 |
|---|---|
| 요구 | 발주사가 수행을 요청한 사항 |

| 과제 | 리서치하여 제안하도록 요청한 사항 |

인용에는 녹취록 타임스탬프를 명시한다. 2차 문서(회의록)만을 근거로 하는 서술은 원문 확인 대상이다.

### 1.2 포트폴리오

#### REQ-F-010 · REQ-F-011 · REQ-F-012 · REQ-F-012a — 뎁스 구조와 콘텐츠·링크 병행

유형 요구 · 출처 녹취록 28:55

김상규 질문(28:32): *"포트폴리오를 보여주는 방식이 보통은 캡처 이미지들로 보여주는데, 저희가 특화해서 할 수 있는 게 있을까요?"*

> "제 생각에는 링크를 보여주면 좋을 것 같은데 저희도 링크가 있지만 이렇게 구성을 했던 이유 중에 하나는 결과적으로 이게 콘텐츠적으로 노출이 돼야 돼요.
>
> 그러니까 어떤 거냐면 에어로케이 개발사라고 했을 때 저는 똑개가 떠야 된다고 생각해요. 에어로케이를 누가 만들었는가를 궁금해하는 사람 분명 있을 거거든요. 근데 그렇게 쳤을 때 누가 개발했는지가 AI가 가져올 수도 있어야 되고 써야 된다라는 거죠. 그러려면 이 콘텐츠가 잘 뭔가 적혀 있어야 되거든요.
>
> 그래서 그런 것들을 콘텐츠 두 가지인 것 같아요. 이렇게 콘텐츠로도 보여주고 그다음에 링크로도 볼 수 있게끔 만들어줘야 될 것 같긴 합니다.
>
> 그리고 뎁스가 무조건 이렇게 한 뎁스 들어와야 돼요.
>
> 그리고 여기에 바로 가기 이렇게 해서 누르면 이제 패밀리케어로 넘어갈 뷰가 보이면 좋을 것 같아."

해석 — "한 뎁스"의 의미

발주사가 자사 사이트 화면을 공유하며 발언했으며, "이렇게", "여기에"는 화면을 가리키는 지시어다. 앞뒤 문맥을 종합하면 다음과 같다.

```
목록  ──1뎁스──▶  프로젝트 상세 (자사 도메인)  ──바로가기──▶  실제 서비스
                    │
                    └─ 색인 대상 페이지
```

| 판정 | 내용 | 근거 강도 |
|---|---|---|
| 최소 조건 | 목록에서 반드시 1뎁스 진입하여 자사 도메인 내 콘텐츠 페이지를 거친다 | 강함 — 바로 앞 문장이 "콘텐츠로도 보여주고"이며, 목록에서 외부로 직접 이탈하면 색인될 콘텐츠가 없다 |
| 최대 조건 | 상세 페이지 아래로 서브페이지를 만들지 않는다 | 보통 — "이렇게"의 지시 대상이 1뎁스 구조이므로 유추 가능 |

"한 뎁스"는 뎁스를 제한하라는 요구가 아니라 뎁스를 확보하라는 요구다. 링크만 걸린 카드 그리드나 캡처 이미지 갤러리로는 GEO 목적을 달성할 수 없다.

REQ-F-012a 도출 근거 — 프로젝트가 빌더 상세에 인라인으로만 노출되고 상세 페이지로의 링크가 없으면, 상세 URL은 존재하나 아무도 링크하지 않는 고아 페이지가 된다. 크롤러가 도달하지 못하므로 본문 500자를 작성해도 무효가 된다. 따라서 카드에 링크가 두 개 필요하다.

| 링크 | 목적지 | 목적 |
|---|---|---|
| 제목 · 자세히 보기 | 프로젝트 상세 | 색인 경로 확보 |
| 바로가기 | 실제 서비스 (외부) | 신뢰 확보 |

#### REQ-F-013 · 본문 4문항 구조

유형 판단 · 관련 §1.11

#### REQ-F-015 · 빌더 양방향 연결

유형 요구 · 출처 녹취록 09:25

> "포트폴리오를 들어갔을 때 여기에 참여한 빌더 분들의 … 참여한 팀원들이 있고 해당 팀원 들어가면 그 팀원이 진행했던 프로젝트 리스트 나오고 이렇게 되면은 조금 좋을 것 같아요."

해석 — 09:25(빌더 → 프로젝트)와 28:55(목록 → 상세 1뎁스)를 그대로 쌓으면 3뎁스가 되어 충돌한다. 빌더 상세에서 프로젝트를 인라인 전개(REQ-F-021)하는 방식으로 해소했다. 요약은 빌더 페이지에, 전문은 프로젝트 페이지에 두어 분량을 달리하므로 중복 색인 문제도 발생하지 않는다(REQ-F-075 self canonical).

#### REQ-F-018 · 데이터 소스

유형 요구 · 출처 녹취록 10:33

> "지금 저희가 포트폴리오가 없다 보니까 … 최대한 저희 쪽에서 지금 똑빌더 … 여기서 진행하고 있는 것 중에 몇 개 가져와서 넣을 거기도 하거든요.
>
> 제가 봤을 때 지금 이 차근차근, 에듀셀파 3%랑 동행케어, 카본벨트 정도는 다 바이브코딩으로 하고 있는 거거든요. 그래서 이런 것들은 넣어도 돼요. 나머지는 개발자들 여러 명 들어가서 보고 있는 거라서 좀 어려울 것 같고요."

출처(빌더 제작물) — 녹취록 09:25

> "저희 팀원분들이 작업했던 내용들 있잖아요. 그거 중에서 AI스럽지 않다라고 판단되는 페이지들을 불러와서 넣는 것도 포트폴리오로 넣는 것도 좋을 것 같아요."

주의 — 혼동 주의 — 녹취록 32:29의 *"실제와 좀 다를 수 있어도 우리를 팔 수 있는 요소"*는 본 항목과 다른 사안이다. 그쪽은 경쟁사 리서치 과제(§1.12 과제 A)이며, 실전 4건 차용은 단지 자체 포트폴리오가 없기 때문이다. 정정 이력 §4.2 참조.

### 1.3 빌더

#### REQ-F-020 · REQ-F-020a · REQ-F-020b — 목록 정렬

유형 팀

녹취록에 직접 근거가 없다. 다음 사업 배경에서 도출한 설계 판단이다.

출처(사업 배경) — 녹취록 01:18, 02:00

> "저희가 장기적으로 그 교육생 분들이 일감을 따서 주는 게 … 브랜드 자체를 AI 빌더 그룹이라고 해서 … 교육과 그리고 실제로 외주 프로젝트 실행과 그리고 커뮤니티를 운영할 거예요."

해석 — 빌더는 기수 단위로 증감한다. 1기 12명에 최적화된 화면은 2기에 재설계가 필요하므로, 처음부터 목록 구조로 취급한다.

> 인원 정정 (2026-08-07) — 1인 포기로 12명이다. **숫자 자체는 설계에 영향이 없으나**, 인원이 실제로 변동한다는 사실이 확인되어 목록 구조 취급의 근거가 강화됐다.

정렬 방식 검토 경위

초안은 "기수별 그룹 + 최신 기수 상단"이었으나 근거가 확인되지 않았다. 오히려 다음 문제가 지적됐다.

| 문제 | 내용 |
|---|---|
| 역효과 | 최신 기수는 경험이 가장 적은 인원이다. 발주자가 처음 보는 영역이 신입으로 채워진다 |
| 실적 역행 | 시간 경과에 따라 실적이 축적된 초기 기수가 하단으로 밀린다 |
| 정보 무의미 | 기수는 발주자에게 의미 없는 내부 개념이다. 발주자의 관심은 기수가 아니라 결과물이다 |

순수 랜덤 검토 결과 — 노출 균등성은 확보되나 세 가지 문제가 발생한다.

| 문제 | 내용 |
|---|---|
| 캐싱 충돌 | 정적 생성 시 순서가 고정된다. 매 요청 셔플하려면 캐싱을 포기해야 하며 REQ-N-001과 조율이 필요하다 |
| 재방문 탐색 불가 | 발주자가 이전에 확인한 빌더를 다시 찾지 못한다. 복수 업체를 비교하는 사용 행태(§2.2)와 충돌한다 |
| 검수 재현 불가 | QA 시 동일 화면이 재현되지 않는다 |

채택 — 일별 시드 랜덤. — 날짜를 시드로 사용하여 하루 단위로 순서를 고정한다. 노출 균등성이라는 취지를 유지하면서 위 세 문제를 회피한다.

기수 그룹핑 제거 — 그룹을 두면 그룹 간 순서를 결정해야 하는 문제가 남는다. 그룹을 제거하고 전체를 단일 배열로 처리하면 해당 문제가 소멸한다. 기수 정보는 카드 배지로 유지한다(REQ-F-020b).

운영 개입 경로 확보 — 운영팀이 특정 빌더를 상단에 고정할 필요가 있을 수 있으므로, 고정 지정 빌더를 셔플 대상에서 제외하는 경로를 남긴다(REQ-F-020a).

#### REQ-F-025 — 표기 수위 혼재 대응

유형 팀

빌더 표기 수위(실명/닉네임, 실사/아바타/미등록)는 개인 선택이므로 목록에 혼재한다. 어떤 조합에서도 그리드가 유지되어야 한다. 이미지 미등록 시 표기명 이니셜 또는 기본 그래픽으로 대체한다(POL-02).

#### REQ-F-022 · 단독 공유 가능성

#### REQ-F-077 · 구조화 데이터

유형 팀 · 출처 REQ-F-078(GEO)의 보조 수단으로 도출

**녹취록 근거가 없다. 팀 판단이므로 반려 사유로 사용하지 않는다.**

목적 — 답변엔진과 검색엔진이 페이지의 성격과 주체를 기계적으로 읽을 수 있게 한다. `REQ-F-078`이 *"답변엔진이 프로젝트 제작 주체를 인용할 수 있어야 한다"*를 P0로 요구하며, 본문 500자는 사람이 읽는 근거이고 구조화 데이터는 기계가 읽는 근거다.

| 타입 | 적용 대상 | 알리는 내용 |
|---|---|---|
| Organization | 사이트 전체 | 회사명 · 로고 · URL · 연락처 |
| Article | P-04 프로젝트 상세 | 제목 · 이미지 · 작성일 · 작성 주체 |

**검색결과 모양은 바뀌지 않는다.** 구글은 `Article` 리치 결과를 뉴스 · 블로그 · 스포츠 기사로 한정하므로 프로젝트 소개 페이지에는 리치 결과가 표시되지 않는다. 검수 기준의 *"Rich Results Test 오류 0건"*은 **마크업이 유효한지를 확인하는 것이지 검색 노출 개선을 보장하지 않는다.**

값어치는 `Organization`이 크다. 브랜드 검색 시 검색엔진이 회사 정보를 인식하며, 이는 도메인 확정(D-5) 이후 적용한다.

우선순위 P1인 이유 — 매뉴얼 §05의 테크니컬 SEO 6종에 포함되지 않는다. 6종을 먼저 완료하고 여력이 있을 때 적용한다.

### 1.11 본문 작성 가이드 (4문항)

유형 판단

도출 배경 — REQ-F-078(GEO)이 본문 500자 이상을 요구하나, 백지 상태에서 500자 작성은 부담이 크다. 특히 빌더 전원이 반복 충족해야 하는 기준이므로 달성 가능성이 관건이다.

설계 — 4개 질문에 답하는 형식으로 전환하면 자연히 500~700자가 산출된다.

| # | 문항 | 분량 |
|:---:|---|---|
| 1 | 무엇을 만들었나 | 2~3문장 |
| 2 | 왜 필요했나 (문제) | 2~3문장 |
| 3 | 어떻게 풀었나 | 3~4문장 |
| 4 | 결과 | 1~2문장 |

최소값을 800자가 아닌 500자로 설정한 근거 — 기수마다 신규 인원이 동일 기준을 넘어야 하므로, 일회성이 아닌 반복 가능한 기준이어야 한다.

4번째 문항을 유형별로 분기하지 않는 근거

| 근거 | 내용 |
|---|---|
| 독자 관점 | 사이트 독자는 발주자다. 빌더의 학습 과정이 아니라 성과를 확인한다. "배운 것"은 교육생 관점 용어다 |
| 진열 일관성 | 두 출처가 동일 목록·동일 카드 컴포넌트를 사용한다 |
| **구분 표기 부재** | **실전/제작물 구분을 노출하지 않으므로, 소제목이 출처에 따라 달라지면 감춘 구분이 드러난다** |
| 구현 단순성 | 조건 분기 제거 |

작성 주체 판단 — 빌더 본인이 작성한다. 자기 포트폴리오를 영업에 활용하는 것이 빌더의 목적이므로 작성 동기가 존재한다. 단, 실전 사례는 빌더가 작성할 수 없으므로 발주사 제공 자료를 기반으로 팀이 작성한다. **발주사가 라이브 링크 노출 동의와 원본 데이터 제공을 확정했다** (2026-08-07).

### 안건 5 · 포트폴리오 목록 분리 — **분류축 자체가 교체됨**

**분리 여부의 문제가 아니었다.** 발주사 회신 (2026-08-07)

> *"포트폴리오는 실전 사례 / 빌더 제작물 이게 분리되면 안 되고 우린 모두 실전 경험이 있는 빌더로 보여져야 할 것 같아요. 차라리 산업, 도메인별 분리라던지, 서비스 특성에 따른 분리가 맞을 것 같네요"*

`실전 / 빌더 제작물` 축은 **우리 손으로 결과물에 등급을 매기는 구조**다. 사이트 목적이 *"검증된 빌더를 조직이 보증한다"*인데 앞뒤가 맞지 않는다.

**결정** — 두 축의 값을 **하나의 카테고리 목록**으로 관리하고 `axis`로 필터 그룹만 나눈다.

| `axis` | 값 |
|---|---|
| 산업 · 도메인 | 교육 · 커머스 · 의료 · 금융 · 공공 |
| 서비스 특성 | 랜딩 · 예약 · 대시보드 · 커뮤니티 |

계층을 두지 않으므로 관리 화면이 하나로 끝나고, 값을 다른 축으로 옮겨도 구조가 흔들리지 않는다. 프로젝트에 **복수 지정**한다. 값은 임의 지정으로 시작하고 운영 중 조정한다 (팀장 확인).

### 화면 설계(기획 산출물 ⑤) — **작성 완료**

안건 1·5·6이 확정되어 **팀 명의로 확정했다** (ABG-UI-005). 안건 10은 플러그 임베드 영역 내부 사안이라 화면 레이아웃에 영향을 주지 않는다.

와이어프레임은 IA·기능의 시각화이므로 2~3안으로 분기하지 않고 1종으로 합의한다. 매뉴얼 §03이 "확정된 화면 수가 범위 기준선"이라 규정하므로 화면 수가 복수일 수 없다.

> REQ-C-010(주력 1~2안 + 비교 스토리)은 **디자인 시안**에 적용되는 요구다. 화면 설계는 그 대상이 아니다.
